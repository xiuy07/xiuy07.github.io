    软件工程与计算 II 从需求到交付

    理论 案例 作业与验证 放在同一条开发主线上

    从头学习理解用例作业理解顺序图作业设计验证证据

    这份讲义面向第一次系统学习软件工程的同学，以裁判文书论证结构标注系统贯穿项目启动、需求、分析、设计、构造、测试、交付与维护。每一阶段把概念与案例放在一起，解释为什么要做、怎样做、留下什么，以及怎样检查。

    全篇围绕同一条规则反复推导：命题集先裁定并冻结，关系标注再基于统一版本展开。把这条规则从用例讲到状态、接口、数据库和测试，就能理解各份工程产物为什么必须互相一致。

    阅读约定：资料明确、版本差异、教学示例和待确认事项分别标注。演示不是已运行系统，示例不是老师新增的提交规定。建议从第0章顺序阅读，做作业时通过目录和搜索回查。

    0 从一条需求看懂软件开发全程

    0.1 软件项目最后交付的是什么 #

    假设老师说：“做一个系统，让两名标注员分别标注裁判文书，由裁定者形成统一结果。”你可能马上想到做网页、建数据库。先停一下：两个人什么时候能看对方的结果？命题都没确定，关系应该连到谁？裁定后还能修改吗？这些问题决定代码应当怎样工作。

    软件不仅包括可执行程序，还包括支撑运行的数据、配置和必要文档。一个能在你电脑上打开的页面，只证明部分程序能运行。完整交付还要让别人理解怎么使用、能够重现运行，并知道出问题怎样恢复。

    项目启动→需求获取与分析→需求规格与确认→体系结构→交互与详细设计→构造与集成→测试与交付→维护与演化

    这条顺序是理解上的主线。真实开发经常反复：画原型发现需求不清，就回去确认；写测试发现接口设计有问题，就修改设计。测试思考、质量保障、配置管理和需求追踪从项目开始就存在。

    0.2 每一步解决一个不同的问题 #

    阶段核心问题典型产物
    项目启动谁来做，在什么限制下做范围、分工、计划、仓库、风险清单
    需求工程用户到底需要系统做什么用例、业务规则、分析模型、需求规格
    体系结构设计系统分成哪些大块，如何协作模块图、接口、部署图、架构决策
    详细设计每块内部由哪些对象完成任务设计类图、详细顺序图、算法、数据设计
    软件构造怎样把设计实现并持续集成代码、构建配置、单元测试、评审记录
    验证与交付有没有做对，别人能否使用测试证据、部署包、操作与维护文档
    维护与演化变化来了，怎样可靠修改变更记录、修复、新版本、回归结果

    0.3 用一条需求贯穿全书 #

    本讲义反复使用一个案例规则：命题集裁定并冻结后，才能开始关系标注。需求阶段要定义“冻结”的条件；设计阶段要确定谁控制状态；实现阶段要阻止非法请求；测试阶段要证明冻结前不能写、冻结后引用正确版本；维护阶段要处理命题变更对旧关系的影响。

    你暂时不必懂法律论证。把“命题”理解为从文书中识别出的判断，把“关系”理解为这些判断之间的支持、反对等连接即可。系统负责保存与检查结构，人的业务判断决定连接在语义上是否成立。

    本章自测：“页面上按钮变灰了”足以证明冻结前不能新增关系吗？

    展开答案

    不足。用户可能直接调用接口，页面状态也可能过期。还要检查服务端是否依据权限、阶段和版本拒绝写入，以及数据库里是否没有新增关系。

    0.4 怎样把这份讲义当作一门课来学 #

    第一次通读时，先抓住一条线：用户问题 → 可验收需求 → 分析模型 → 设计契约 → 实现 → 验证 → 交付 → 变更。每到一个阶段，问自己“输入是什么、我需要作出什么决定、留下什么产物、下一步靠它做什么”。这样就不会把用例、类图和数据库当成彼此独立的几次作业。

    本讲义把一般方法与裁判文书论证结构标注案例放在同一章。概念讲解回答为什么，案例讲解说明怎么落地，练习检查你能否自己推导。第一次看不懂框架名可以先略过；业务对象、状态、版本和验收条件不要跳过。

    本讲义的边界：标注指南用于说明业务规则，原型用于理解交互意图，已有用例和顺序图用于分析修订。接口、表名、代码和测试编号若标为教学示例，就不是对已运行系统的描述。未决策问题保持待确认，不通过编写讲义替需求方作决定。

    0.5 准备一张贯穿全程的练习纸 #

    在纸上写出五栏：规则、谁执行、操作条件、成功变化、失败保证。以“冻结后才能标关系”为第一行。接下来每章只为这条规则增加一层解释，直到能把它从业务目标讲到数据库和测试。你不需要一次记住整套软件工程术语。

    资料对应 课程概览 软件工程基础 软件交付。

    1 先读懂案例 从原文到法律论证结构

    1.1 系统到底处理什么 #

    系统面向裁判文书说理部分，把原文分成要素，为要素标类型，再描述命题之间的关系，最终形成结构化数据和论证图。案件基本信息与法律论证标注是两个相关但不同的任务：案号、法院、日期帮助管理材料，命题与关系表达说理结构。

    以指南中的劳务报酬例子为基础，先只看三段：P7“根据原告提交的欠条、微信转账记录可以认定”，P8“被告尚欠原告劳务报酬11000元”，P9“被告应向原告支付该11000元”。指南把前两者列为SF，P9列为SM。这里是在学习所给指南的标注方式，不进行案件法律意见判断。

    要素类型和论证角色不是同一回事。SF、SM等是判断性质；“前提、子结论、结论”是某个判断在关系结构中的作用。指南第3节说明，后者不作为独立标注项目，而由关系结构分析推导。

    1.2 切割不是遇到标点就结束 #

    修订指南2.3节要求先按句号与分号初切，再检查其中逗号分隔的子句。连续子句性质相同、相互没有明显支持或反对关系时，可以作为一个要素；性质不同或存在相关论证关系时，需要进一步区分。

    引号内容有特殊切割要求；非论证成分一般按句号处理，指南还列出判决依据、态度声明等例外；“因此”“综上来看”等过渡语词与后面的第一个要素一起切割。自动切割只能提供候选，人工仍需依规则检查。

    为什么先统一切割？如果一个人把两句话标成一个要素，另一个人分成两个，即使他们都写SF，也不能直接逐行比标签。先对齐边界，再比较类型，能减少把同一个边界问题重复算成多种差异。

    1.3 命题类型怎样记 #

    维度个别判断一般判断
    事实SF，具体案件对象的事实GF，经验、常识、科学规律等一般事实
    规范SM，具体主体的法律意义评价GM，一般规范基础

    GM在修订指南中分为GM-L法律条文、GM-I法律解释、GM-U习惯与行业惯例、GM-M道德与价值观念、GM-O其他规范判断。SM中单列SM-C合同及合同解释。指南所称“司法解释”属于其法律条文类别，不应因为名称带“解释”就机械标为GM-I。

    还要保存非命题要素：IS争议焦点、AS态度声明、SS总结性陈述、JG判决依据、JD判决结果、Non-O其他非论证成分。不能把所有文本强塞进四类命题，也不能把这些要素毫无区别地放进命题关系端点列表。具体标注范围按材料类型与确认规则确定。

    1.4 五种关系先理解含义 #

    关系读法需要避免的误解
    S(P1,P2)P1为P2成立提供理由不是简单的上下句相邻；不自动补全传递边
    A(P1,P2)P1反对P2出现“但是”不一定构成反对，需要找到实际反对对象
    J(P1,P2)两者共同构成缺一不可的组合两条可独立支持的理由不应强行组合
    M(Ps,Pg)个别判断与一般判断形成匹配，方向由个别指向一般不能当作没有方向的任意配对
    I(P1,P2)两者语义同一一般规则的具体化不等于同一

    指南要求J按序号组织，允许发生在不同命题要素之间；不能把“通常同类”实现成“类型不同一律禁止”。I要求同一而非具体化，并说明后续使用最大序号命题继续标注。涉及内容语义的判断由人完成，程序的类型检查只是辅助。

    1.5 嵌套关系为什么影响软件设计 #

    先看两个独立支持：S(P1,P3)、S(P2,P3)。它们表示每一条都是自己的理由。S(J(P1,P2),P3)表示两者合起来才支持P3，含义不同。

    再看A(P4,S(P1,P3))：P4攻击的是“P1支持P3”这条连接，而不是直接攻击P1或P3。如果数据表只有fromProposition和toProposition两个字段，就保存不了这个对象。

    一个教学用分步结构是：R1=J(P1,P2)，R2=M(R1,P3)，R3=S(R2,P4)，R4=A(P5,R3)。P3需为相应一般判断，P1、P2及整个结构是否满足语义，仍由标注规则与人判断。这串表达说明：关系本身也可能成为另一关系的操作数。

    1.6 图示是数据的一种表达 #

    命题用矩形，图中主要显示序号；S用实心圆与有向边，A用空心圆与有向边，J用带加号圆与无向连线，M用带加号圆与有向边，I用矩形框内斜线。仅用不同颜色的直线不能完整实现指南图元规范。

    修订指南6.3节对某些嵌套做显示简化：组合与匹配可能共享一个加号节点；匹配再支持时可以从被匹配的一般判断处画支持起点。显示简化不等于逻辑数据删掉中间关系。数据库仍应保留可重现的完整层级。

    本章自测：为什么一个只能“选两个P编号并连线”的关系编辑器不够？

    展开答案

    J与I可能有多个成员；M与S可以包含其他关系；A可以指向支持关系。编辑器需要按关系类型提供成员集合或有方向的操作数，并允许引用合适的关系对象。

    1.7 一个可以反复使用的完整小样本 #

    为了让后面的模型都有具体对象，使用指南文书一中的四个命题，重新编号为E1至E4。这里的E表示示例稳定ID，不是指南原有的显示序号。

    稳定ID示例文本指南中的位置与类型
    E1原、被告之间系劳务合同关系原P4，SM
    E2原告已依约提供劳务原P5，SF
    E3当事人应当按照约定全面履行自己的义务原P2，GM-L
    E4被告应按照原、被告之间的约定给付劳务报酬原P6，SM

    按照指南示例的组合思路，可用R1=J(E1,E2)、R2=M(R1,E3)、R3=S(R2,E4)逐层表达。先把具体关系保存在结构里，再按指南图示规则生成显示。这是对所给样本的教学重编号，不能把它作为所有文书都应具有的固定推理模板。

    现在让甲乙分别完成切割和类型标注，裁定者确认统一结果，生成PV-1。关系标注员丙丁的关系版本都引用PV-1。他们可以对R3是否成立有不同答案，但至少讨论的是同一批E1至E4。若甲的E2与乙的E2来自不同切割，直接对比关系编号就会失真。

    1.8 实际操作时先检查哪一层 #

    先问选中的原文区间是否对；再问它是命题还是非命题；再问命题性质；再问关系类型、方向和嵌套；最后核对图示。前一层错误会传播到后一层。例如把两个命题误合并，可能同时表现为“标签不一致”“关系缺失”和“图中少节点”，它们未必是三个独立缺陷。

    练习 一个边界错误为什么会造成多项差异

    假设甲把“E1文本，E2文本”切成一个要素，乙切成两个。先识别这是边界与对齐问题，不能直接认定甲少标了一条J、一个M和多个标签。应根据确认的对齐规则先还原比较单位，再分类报告后续差异。

    资料对应 标注指南v1.2修订版第2至7节。

    2 项目启动 团队 范围 质量与配置

    2.1 软件工程研究怎样持续做成软件 #

    软件工程强调用系统化、规范化、可度量的方法开展软件开发、运行和维护。通俗地说，就是让“做出满足需要的软件”成为团队可以规划、检查、复现和改进的工作。

    小程序的主要难点可能是某个算法。系统变大后，难点还包括：不同人对需求的理解不一样；一个模块改动影响其他模块；运行环境不同；人员更换后无人理解旧代码。软件工程用需求、设计、管理和验证来控制这些问题。

    软件具有复杂性、易变性和不可见性。屏幕截图能展示界面，却无法直接展示内部依赖、状态和数据一致性，所以需要模型、文档、代码结构和测试证据帮助大家理解它。软件不会像机械零件那样物理磨损，但持续修改会引入结构退化与缺陷，运行环境也会变化。

    2.2 几个经常混淆的词 #

    名称它回答什么本案例中的例子
    需求系统需要提供什么能力和约束未冻结时拒绝新增关系
    分析怎样理解问题和业务概念找到命题版本、关系版本、裁定等概念
    设计怎样组织解决方案由流程服务协调冻结与开放关系轮
    实现怎样用程序落实方案写状态检查、事务和接口
    验证产物是否满足规定测试未冻结请求被拒绝
    确认规定和产品是否满足实际需要标注员认可分轮流程能够完成工作

    英文 verification 常译“验证”，validation 常译“确认”。不同课件可能也使用“需求验证”统称需求质量检查。理解时看检查对象：是在检查文档内部是否正确一致，还是在与真实涉众确认需要。

    2.3 软件质量不能只看有没有报错 #

    系统能打开，但学生作答会覆盖正式数据，仍然是不合格的。质量既包括符合约定，也包括实际使用价值。正确性、可靠性、性能、安全性、可用性、可维护性等质量目标会影响需求和设计。

    质量保障是一组贯穿过程的活动。需求评审检查“是不是做错了目标”；设计评审检查“结构是否支持目标”；静态分析在不运行程序时检查潜在问题；动态测试通过运行观察行为；配置审计检查发布内容是否与批准的版本一致。这些活动互相补充。

    学到这里应能说清：为什么“代码生成出来”与“软件工程任务完成”之间，还隔着需求确认、集成、验证和交付。

    2.4 项目计划从目标与边界开始 #

    先说明“给谁解决什么问题”，再约定首版范围。对标注系统，可以先让一份文书完整经过独立标注、裁定、冻结、关系标注和导出。批量统计是否进入首版，应依据时间和需求决定。

    范围、时间、成本互相影响，质量是约束下必须管理的结果。时间和人数固定时，新加功能往往意味着删减其他范围、延后交付或增加风险。不能仅靠“大家再努力一点”消除工作量。

    把工作拆成可交付任务，比“前端一个人、后端一个人”更具体。例如“完成冻结接口及非法状态测试”就能验收。给每项任务记录负责人、依赖、完成条件和预计工作量；通过里程碑检查重要结果，而非只统计忙了多久。

    2.5 团队结构与分工 #

    主程序员团队由核心负责人集中决策，协调快，但依赖关键个人；民主团队共同讨论，能发挥集体经验，但决策成本可能较高；开放团队结合明确职责与开放交流。选择取决于规模、任务和成员经验，不存在万能结构。

    角色是责任，不一定等于某个固定的人。需求、架构、开发、测试可以分阶段轮换主导，但关键知识需要共享。一个功能至少应有另一名成员能够解释、评审和接手。

    2.6 风险管理要提前产生行动 #

    风险是尚未发生的不确定事件，问题是已经发生的障碍。例如“指南解析可能不可靠”是风险；“今天导入文件报错”是问题。识别风险后，评估发生可能性与影响，安排应对和观察信号。

    对解析风险，行动可以是尽早用三种真实样本做技术试验，并准备人工确认入口。风险清单若只写“加强沟通”“注意进度”，没有责任人和触发措施，就很难起作用。

    2.7 配置管理管理的不只是代码 #

    配置项是需要受控管理的制品，例如需求文档、指南、模型、源码、数据库迁移和部署配置。版本表示某个制品的一次状态。基线是经过评审、作为后续工作依据的受控版本，修改需要约定的变更程序；不是所有 Git 提交都自动构成基线。

    配置管理包括标识配置项、版本管理、变更控制、状态报告、配置审计及发布管理。比如需求已改为六阶段流程，而顺序图、数据库和代码仍按四阶段实现，这就是制品之间不一致，不能只靠“Git 里都有”解决。

    Git 中，工作区是正在编辑的文件，暂存区是准备提交的变更，本地仓库保存提交历史，远程仓库用于团队共享。commit 保存本地历史，push 才把提交传到远程；分支用于隔离工作，合并时还需要检查业务冲突。

    建议在短分支完成一个明确任务，提交后进行评审和自动检查，再合并到主干。具体使用 main、dev 还是其他名称由团队约定。CI 指持续集成中的自动构建和检查；CD 可能指持续交付或持续部署，后者才强调自动进入生产环境，不能混为一谈。

    本章自测：“把命题标签配置文件提交到 Git”能否替代系统中保存每个任务绑定的指南版本？

    展开答案

    不能。Git 管理开发制品，业务数据还需要记录某次任务实际使用的指南版本、原文版本和作答版本。两个层面的版本管理相关，但对象不同。

    2.8 先写一页项目目标 #

    可以用这段教学示例作为讨论起点：“本系统为法学研究与教学提供论证结构标注能力。正式模式形成经过多人独立标注和裁定的可追溯结果；教学模式支持基于教师标准的练习与反馈。首版优先完成一份文书从创建到导出的闭环。”

    这段话定义目标，后续还需要明确首版是否覆盖批量上传、OCR、自动差异比对、统计和多种导出。不要把原型里展示过的全部入口默认变成首版必须做完的范围。

    2.9 分工按交付链路组织 #

    可以让不同成员分别主导需求与规则、服务端与流程、工作台与图示、测试与交付，再轮换主导和交叉评审。每项功能有一个责任人，同时安排另一人能解释关键行为。

    把“大作业”拆成“指南版本绑定”“独立提交与隔离”“命题裁定冻结”“关系嵌套编辑”“教学练习”“终稿导出”等任务，每项写输入、产出与完成条件。“开发后端”范围太大，无法反映实际完成程度。

    2.10 仓库最先应该有什么 #

    README说明目标、目录、环境和运行入口；docs保存需求、设计、决策与过程记录；src保存源码；tests保存验证代码；部署目录保存迁移和配置示例。目录名称可自定，重要的是别人能找到。

    先让最小项目可构建，并在CI中运行编译和基础检查。随后让每条真实业务规则进入相应测试。需求、指南与模型都需要版本记录，不能只把最终代码提交一次。

    2.11 P0和P1哪些内容可借鉴 #

    CampusHub的P0要求团队章程、轮换、工具评估、签署AI协作契约、Git与CI；契约模板还列出人工审查、提交标记和手写核心函数要求。P1列出调研、SRS、用例、用户故事、AI盲区对比和反思日志。

    这些文件中的4人、10周、20份问卷、8人次访谈、15个用例或故事等，属于该方案的原要求。它们不能仅因在同一个课件目录中，就自动成为法律论证作业的评分标准。可借鉴方法，数量和提交规定要对应当前任务书。

    本章产出：目标与范围、分工、初始计划、仓库、环境、风险、已确认的过程规则。此处讲的是你应该准备什么，没有假定这些材料已经存在。

    2.12 把目标拆成可验收的任务 #

    “本周做完冻结功能”还太粗。可拆成：确认冻结条件；更新用例与状态；定义冻结请求和错误；实现快照与状态的共同提交；实现并发控制；补充成功与拒绝测试；在页面中显示新基准。每个任务都有产物与检查方式，才能知道卡在哪里。

    估算时区分工作量和日历时间。一个需要6人时的任务，若依赖周五的业务确认，未必周二投入两个人就能提前完成。记录依赖、缓冲与主要不确定性，比填写一个过于精确却没有依据的日期更实用。

    完成定义示例：代码已合并；接口契约与SRS一致；正常和非法路径已实际验证；别人能按说明运行；相关模型已更新。它是团队关于“完成”的约定，不是要求每个小修改都写一篇大报告。

    2.13 质量 风险和配置怎样一起工作 #

    风险清单说“回退可能破坏关系引用”，设计就要安排版本策略；测试计划就要包含旧版保留与影响关系复核；配置管理就要让需求、模型、代码与验证记录属于同一次受控修改。三张表彼此没有关联，就容易只剩形式。

    3 需求基础 把目标写成可验收的约定

    3.1 需求有三个常用层次 #

    业务需求说明组织为什么做项目，例如“建立经过复核的法律论证数据集”。用户需求说明用户为了这个目标要完成什么工作，例如“裁定者希望比较多人结果并确认统一命题集”。系统级需求进一步规定系统应提供的具体行为，例如“所需提交不齐时，冻结请求应被拒绝并列出缺失人员”。

    三个层次由目的逐步走向具体行为。不能把“使用 MySQL”当成用户的业务目标，也不能只写“提高效率”就期待开发者实现出来。

    3.2 层次与类型是两条分类轴 #

    功能需求说明系统做什么。质量需求说明做到什么程度，例如在约定数据规模和环境下的响应时间。约束限定允许的解决方案，例如必须使用某个接口或指定部署环境。项目需求限制进度、成本、人员；过程需求规定怎样开发，例如提交评审记录。

    “裁定者能冻结命题集”是功能；“普通用户不能越权冻结”也有可执行的授权行为；“系统必须保护数据访问”属于安全目标。安全需求可能同时包含功能机制和质量约束，所以不要机械地把一切安全内容都塞进一句非功能需求。

    3.3 需求工程的活动 #

    需求开发通常包括获取、分析、规格说明和确认。需求管理处理版本、优先级、变更和追踪。获取时发现事实与需要；分析时识别冲突、概念和边界；规格说明把结论写到足够明确；确认时让相关人员检查是否准确可行。

    这几个活动会循环。比如原型让老师发现“命题和关系必须分轮裁定”，你就要重新分析状态，再更新规格和模型，重新确认。不是第一次写完需求文档后，需求工作就结束。

    3.4 需求怎样才算写清楚 #

    “系统快速生成正确图示”包含两个问题：“快速”没有指标，“正确”没有判定依据。更好的写法应说明输入规模、运行环境、目标时间、图元规则、失败行为和验收方式。

    例如，教学用的性能目标可以暂定为“在约定电脑、100 个命题与150条关系的样本上，刷新图示的第95百分位耗时不超过2秒”。这些数字只是示范如何写可测量要求，不是这项课程作业已经确认的指标。真正数值需要需求方与工程方商定。

    一条好需求通常应必要、明确、完整到足以实施、前后一致、可行、可验证、可追踪。尽量一条只表达一个可独立验证的要求；给它编号，记录来源与状态。

    小练习：把“标注员可以修改数据”改写成更明确的一句话。

    参考答案

    被分配到命题轮的标注员，在该文书处于命题标注阶段且个人版本尚未提交时，可以修改自己的要素类型；修改成功后只更新自己的草稿，不改变其他标注员或已冻结版本。提交后的修改策略另行规定。

    3.5 同一目标逐层改写一次 #

    业务目标可以写成“形成不同人可以比较、结果可以重现的论证数据”。用户需求是“关系标注员希望基于裁定后的共同命题集工作”。系统需求则要进一步说明：关系写入请求引用哪份基准、何时允许、错误时返回什么、存储不得产生什么变化。

    不要把层次展开误解为不断加字。每往下一层，都应消除一种不确定性。如果三个层次只是分别写“提高质量”“提升标注质量”“系统保证高质量标注”，并没有真正变得可实现。

    3.6 把不可验收形容词拆开 #

    “安全”可拆成身份认证、文书分配、轮次职责、状态门禁、数据范围和审计。“快速”要指定数据规模、环境、统计口径和阈值。“准确”要区分结构合法、规则提示、人工语义判断和对教师标准的比对，不同准确性的判定对象不同。

    练习 “系统自动正确裁定全部法律关系”有什么问题

    它没有定义正确答案、适用范围和可接受错误，而且把人的法律语义裁定责任转给了不明确的自动能力。可先约定系统自动检查引用和结构、展示疑似差异，由有职责的人确认语义。若另有AI建议功能，应单独约定候选输出、人工复核和评估口径。

    4 需求获取 访谈 原型 冲突与决策

    4.1 先找涉众 再问具体工作 #

    涉众包括使用系统的人，也包括提出目标、制定规则、维护系统或承受结果的人。标注员、裁定者、教师、学生、负责人和维护者关注点不同。只问开发同学，会遗漏真实工作的困难。

    系统边界说明哪些责任由本系统承担，哪些留给人或外部系统。例如系统可展示分歧和保存专家结论，但法律语义争议仍由相关人员裁定。边界明确后，再判断外部参与者和系统接口。

    4.2 不同方法寻找不同的信息 #

    方法适合发现什么使用时注意什么
    面谈目标、规则、例外、理由让对方讲实际发生过的任务，避免诱导回答
    观察熟练用户没说出的操作习惯记录情境、材料和步骤，观察成本较高
    文档审查已有规则、字段、术语、历史矛盾文件可能过时，示例也可能有笔误
    问卷较多人群的分布、偏好、常见问题题目需要清楚，样本不能随意代表所有用户
    原型模糊流程与交互方案给用户任务去操作，记录行为而非只问好不好看
    头脑风暴候选方案、潜在需求产生想法后还需要筛选和确认

    访谈可以先开放提问：“请讲讲上次两名标注员意见不同时怎样处理。”再追问：“谁有最终决定权？材料不齐怎么办？”最后封闭确认：“所以冻结前关系轮不能开始，对吗？”原始记录和整理后的结论要区分保存。

    4.3 原型有不同用途 #

    探索式原型帮助弄清需求；实验式原型检验技术可行性或效果；演化式原型以能够持续增强的资产逐步形成系统。需求探索原型常用临时状态与假数据，不能未经工程处理就当生产实现。

    你的 HTML 原型可以帮助讨论冻结按钮、任务入口和教学模式。它显示“导出成功”，只说明设计者希望表达这个反馈。只有实际产生可读文件，才能证明导出功能完成。

    4.4 冲突不是坏事 隐藏冲突才危险 #

    同一需求可能同时写着“只存最后提交”和“保留历史版本”。先记录各自来源，再说明冲突影响哪些业务，提出选项，交由有权决定的人确认。不要悄悄挑一个写进代码。

    疑问清单只是待办列表。它需要逐条转成“问题—决定—依据—责任人—日期—影响范围”的决策记录，才形成闭环。AI 可以帮助发现矛盾、草拟问题，不能把它生成的回答记成用户已经确认。

    4.5 先从疑问清单选出影响建模的项目 #

    案例疑问清单已经按角色、文本、标签、切割、关系、裁定、导出、版本和教学等模块组织。学习时不要一次背107条。先找“如果不决定，就会使模型相互矛盾”的问题。

    例如RQ-18影响标签层次；RQ-31影响原文副本与索引；RQ-48影响嵌套操作；RQ-69影响是否实现自动比对；RQ-79与RQ-98影响回退和历史保存；RQ-101影响切割指标。清单中的阻塞分类是原文的整理判断，不代表本讲义已经替需求方作出决定。

    4.6 核对最关键的版本差异 #

    问题材料中的不同说法讲解与处理
    合同标签初始需求和第一次用例为GM-C；修订指南为SM-C讲指南业务时采用SM-C；旧作业需同步修订，不能宣称新指南本身仍是GM-C
    切割标点修订指南为句号和分号初切；原型提示句号初切需统一执行规则并处理指南中的例外
    切割阈值修订指南为二人一致性超过80%；原型为差异度不超过10%必须定义公式和口径，二者不能直接互换
    差异比对需求正文要自动识别，补充答复说人工比对；原型及后续分析有自动预筛自动能力的实现范围仍需确定，裁定不能被预筛替代
    最终确认早期用例写全一致自动入库；后续分析要求人工检查完整性将零差异与最终确认分开，并确认正式口径
    历史保存初始需求提只保留最后提交；指南与后续分析要求历史追溯明确草稿、提交、裁定、冻结和终稿分别保留哪些版本
    变更与再导入早期说不可回退，又要求导出再导入；后续分析提出新版本回退定义再导入是新任务、教学材料还是受控修订
    原文修改普通标注描述含临时修改；补充解释关联学生独立页面区分正式原文与教学副本，变动后重建索引基准

    4.7 阈值问题要问到能算为止 #

    “一致性80%”还缺比较单位、公式、对齐方式、遗漏处理和人数推广。以边界集合为例，A切出边界{10,20,30}，B为{10,25,30}，交集2个、并集4个，若采用Jaccard相似度则为2/4=50%。这个计算只是公式示例，并非指南已指定的算法。

    若另一个指标按字符区间重叠计算，结果可能不同。因此不能推断“一致性超过80%”就是“差异度低于20%”，更不能拿它替换原型的10%。即使公式是互补的，也还要确认严格大于与不超过的边界区别。

    4.8 访谈应该怎样问 #

    找标注员走一次实际切割与提交，找裁定者走一次分歧处理，找教师走一次练习发布。围绕具体材料追问：遗漏由谁补；两人不一致怎么办；已经冻结后发现错字怎么办；学生关系练习的基准是什么；导出再导入的目的是什么。

    访谈后把结论写回决策记录，例如“DR-03：关系阶段命题错误采用新修订，不覆盖旧冻结版；影响需求FR-04、SD1回退分支、版本表及回归测试”。若尚未访谈，就标记待确认，不编造已经签字的结论。

    4.9 需求决策记录的完整例子 #

    可以把“是否自动比对”记录为一个候选决策，而不是藏在段落中：问题是自动识别与人工比对在材料中冲突；备选项是仅并排展示、自动预筛后人工确认、全自动裁定；影响是算法、界面、测试及责任边界。由需求方确认采用哪一项，记录依据与适用范围。

    若最终采用自动预筛，也要继续确定：边界不同怎样对齐；关系成员不同怎样比；嵌套等价是否按结构或表达式判断；零差异是否仍人工确认。一个“是”字还没有解决具体契约。

    4.10 原型评估脚本比泛泛讨论更有用 #

    给裁定者一份两人切割不同的文书，请他完成统一切割，再问他怎样知道当前修改影响谁。观察是否找不到入口、是否误以为已经冻结、是否看不见未完成条件。记录“遇到了什么、用户怎样理解、系统怎样反馈”，再形成需求或交互修改。

    访谈者不要提前说“这个按钮当然就是提交”，否则会把自己的解释当成界面本身的可理解性。让用户先独立完成，再追问原因。

    5 用例建模 从角色目标到完整场景

    5.1 先用自然语言讲一个完整场景 #

    用例描述外部参与者通过系统完成某个有价值目标的交互。名称通常用“动词＋业务对象”，例如“发布标注任务”“提交命题标注”“裁定并冻结命题集”。“点击按钮”“调用数据库”通常粒度太低。

    参与者是与系统交互的角色，可以是人，也可以是外部系统。数据库若是本系统内部组成部分，就不作为用例图的外部参与者。一个真实用户可能拥有多个业务角色。

    5.2 用例描述比椭圆图更重要 #

    详细用例通常包含名称、目标、参与者、触发、前置条件、基本流、替代或异常流、后置条件与业务规则。前置条件是场景开始前已经成立的事实；异常流说明执行中可能失败的步骤；成功保证说明完成后必须成立什么。

    例如“冻结命题集”：前置条件是当前用户有该文书的命题裁定职责且处于待裁定状态。基本流是打开裁定结果、确认完整性、请求冻结、系统校验并生成冻结版本。若提交缺失或冲突未解决，系统拒绝冻结，保留裁定草稿并指出原因。

    写基本流时交替描述“参与者意图”和“系统可观察响应”。不要把 SQL、框架类名提前放进用户需求；也不要只写用户点击而没有系统结果。

    5.3 用例图中的关系 #

    普通关联表示参与者参与某个用例。include 表示基础用例执行时包含被复用的用例行为，箭头从基础用例指向被包含用例。extend 表示在特定条件和扩展点上补充行为，箭头从扩展用例指向被扩展的基础用例；基础用例本身应有独立意义。泛化从较特殊的角色或用例指向较一般者，使用空心三角箭头。

    “先冻结，再标关系”是流程约束，不是 include 或 extend 的理由。可以把冻结写为关系标注的前置条件，再用活动图或状态图表达先后。登录也不必被每个用例机械地 include；若会话已经建立，写为前置条件往往更清楚。

    5.4 用户故事与验收标准 #

    用户故事用简短语言表达角色、能力与价值：“作为关系标注员，我希望在统一的冻结命题集上标注，以便不同人的关系结果能够比较。”它适合排优先级和安排迭代，但还需要讨论及验收标准补足细节。

    可以用 Given—When—Then 写验收：“给定命题集尚未冻结，当用户提交关系创建请求时，则请求被拒绝，且不产生关系记录。”这三段分别是准备条件、触发动作与可观察结果。不要把同一段实现代码换一种语言当验收标准。

    MoSCoW 把候选范围分为必须、应该、可以和本次不做。优先级要反映用户价值、风险和依赖，不应把所有功能都写成必须。

    本章自测：“生成关系图”一定是“关系标注”的 include 吗？

    展开答案

    不一定。要看目标粒度和行为定义。如果它只是系统在标注过程中的一个内部步骤，直接写在用例流程中即可；只有作为有意义且可复用的行为抽取时，才考虑单独建模。

    5.5 案例用例图已经在回答谁完成什么目标 #

    drawio中包含任务创建者、标注员、裁定者、学生等角色，并列出导入文本与指南、配置、分配、命题与关系标注、裁定、导出、独立练习和反馈。它帮助划分系统外部责任，不能单独表达六阶段先后。

    按后续流程修订时，可以展开命题与关系两种标注职责、两种裁定职责，并补足教师发布标准与练习的目标。一个人兼任多个职责，不妨碍模型把这些责任分清。

    不要为了用例数量把“选文本”“点击确认”“写数据库”都变成独立椭圆。先问用户完成什么目标，再决定哪些公共行为值得抽取。流程顺序移交给活动图、状态图和用例前置条件。

    5.6 UC2 从文件导入标注指南 #

    原稿含义：任务创建者上传指南，系统解析标签和关系，显示摘要，经确认后初始化配置并记录版本。原稿有不支持格式、解析失败、人工调整与已有体系覆盖等扩展，说明你已考虑主路径之外的行为。

    需要同步的内容：原稿后置条件仍列GM-C和四类命题，按修订指南应说明SM-C及非命题要素；解析不仅提取名称，还需考虑方向、嵌套和图示规则。导入文件不等于解析结果已经正确，候选结果需要人工核对。

    教学用改写流程：创建草稿任务；上传指南；登记原始文件与候选版本；解析或人工整理候选配置；显示摘要和冲突；创建者核对确认；系统绑定一个确定版本。解析失败不绑定候选，保留草稿允许重试。

    “覆盖已有体系”必须加条件。任务已有作答时，直接覆盖会改变旧数据含义；更安全的待确认方案是登记新版本并明确迁移范围。任务未发布且无相关数据时，是否允许更换绑定也应写清楚。

    5.7 UC6 命题标注 #

    原稿含义：标注员选取文本，系统编号，选择类型，显示全文并更新图。原稿明确按原文顺序编号和显示全文，这两个要求应该保留。

    为什么要拆开：原稿把学生作为标注员的一种情况，又允许修改原文，容易使正式数据和练习副本边界不清。后续分析已采用教学独立模式，修订时应分别描述正式命题用例和学生练习用例，而非只在同一用例里加一个E5。

    正式流程还需要前置“统一切割已确认”，约束“只修改个人未提交版本”，提交时检查必填与覆盖，成功生成个人提交快照。命题轮内不能写关系；命题冻结后旧版本不能直接改。

    “先编号后补标签”可以作为草稿行为，但提交时哪些未标项允许存在要明确。按原文重排序时只改变显示序号，不改变稳定ID。删除还应考虑依赖，不能默认把后续引用静默移到另一个命题上。

    5.8 UC12 裁定关系标注 #

    原稿含义：裁定者并排看多人结果，人工选择认可结果或重标，逐条确认后形成终稿。原稿同时写“至少一名标注员已完成”和“多人完全一致自动进入最终库”。这些条件要与后续双人独立、分轮和人工完整性检查统一。

    教学用新前置条件：当前文书处于关系待裁定；本轮所需提交齐备；它们引用同一有效冻结命题基准；当前用户有本工作项关系裁定职责。若有特殊单人配置，要作为经过批准的例外写清，不能由“只收到一份”自动降级。

    基本流可写为：读取原文和冻结基准；展示各个人关系版本；按范围人工比对或使用已确认的预筛；对差异择一、重标或提交专家；复核方向、引用、遗漏与图示；确认并生成终稿快照。零差异不自动证明没有共同遗漏，仍按最终确认规则处理。

    若关系裁定时发现命题有误，应发起命题修订流程，不让关系裁定者顺手覆盖已冻结基准。成功后置条件是有完整可追溯终稿，失败保证是现有快照不被破坏。

    5.9 交作业前怎样检查一个用例 #

    逐项问：角色和目标清楚吗；前置条件是否与状态模型一致；每个动作后有没有系统响应；异常有没有恢复方式；成功与失败分别留下什么数据；条目有没有夹带未确认规则；标签和术语与其他文档一致吗。

    本章产出：更新后的角色与用例图、UC2、UC6、UC12，以及必要的教学用例。此处给的是理解与修订方法，不声称已经修改原始Word文件。

    5.10 一份写完整的冻结用例 #

    以下是教学用例UC-FREEZE，不与旧作业UC编号强行对应。目标是形成后续关系轮共同引用的只读命题基准。主参与者是本工作项的命题裁定者。触发是裁定者请求冻结。前置条件是身份已认证、拥有当前工作项职责且工作项处于命题裁定阶段。

    基本流可以这样写：1 系统展示当前裁定修订、所需提交和待处理事项；2 裁定者检查结果并确认冻结；3 系统读取当前有效状态并校验提交、切割、裁定与完整性；4 系统生成只读命题快照，记录来源版本与操作者；5 系统将该快照设为关系轮基准并返回版本与状态；6 界面显示冻结完成及关系轮入口。

    替代流A：提交不齐或仍有待处理项，系统拒绝冻结，列出问题，裁定草稿与工作项状态不变。替代流B：页面修订过期，系统返回冲突，提示重新读取后检查，不把用户确认应用到另一份数据。替代流C：同一已冻结修订重复请求，按约定返回已有结果，不再创建冲突快照。替代流D：保存失败，相关写入共同回滚，关系轮不能提前开放。

    成功保证：存在可读取的冻结基准，相关关系工作项引用确定版本。最小保证：失败不破坏既有提交与裁定结果。业务规则：冻结版不可原地覆盖，后续修订走受控版本流程。这里的并发与幂等细节还要在设计与接口契约中进一步规定。

    5.11 从用例到验收 不是把步骤直接照抄成测试 #

    基本流给出正常目标；替代流产生拒绝、恢复和重复请求测试。测试还要检查数据变化，例如“没有生成第二个冻结快照”。同样的屏幕提示可能对应不同后端行为，不能只检查最后一句文本。

    练习 用例前置条件与执行校验为什么可能都出现权限

    用例前置描述典型场景开始时假定成立的条件，真实接口仍需在执行时验证，因为页面可能过期，调用者也可能绕过页面。需求模型中的假设不能自动替代安全与一致性机制。

    6 领域建模 找到概念 身份和关联

    6.1 领域模型描述问题世界 #

    领域模型也常称概念类图或分析类图，帮助团队统一业务概念。分析阶段主要关注“有哪些业务对象、属性和联系”。课程中的概念类图通常只列必要属性，不展开实现方法。

    在标注系统中，“文书”“标注任务”“个人标注版本”“冻结命题版本”“关系”“裁定记录”都是候选概念。“提交按钮”“MySQL连接”“某个前端组件”通常不是核心领域概念。

    可先从用例中找名词，再筛选：它是否有业务意义？是否有独立身份或状态？是否只是一段描述？名词抽取是起点，不能遇到名词就建类。

    6.2 关联和多重性怎样读 #

    “一份文书有多个个人标注版本”表示文书与标注版本有关联。关联一端的多重性说明：固定另一端的一个对象时，这一端允许有多少对象。1 是恰好一个，0..1 是可无可有，0..* 是任意多个，1..* 是至少一个。

    用户与文书可能多对多。若分配本身还需要保存轮次、职责、生效时间，就应将“分配”作为业务概念，而不是只画一根无信息的多对多连线。

    组合表示很强的整体与部分关系，实心菱形画在整体端，部分的生命周期依附于整体。普通关联已经能表达很多情况，不要因为“数据库有外键”就全部画组合。继承表达稳定的“是一种”，不是代码复用或字段相似的同义词。

    6.3 身份与显示顺序必须分开 #

    P1、P2、P3 是读者看到的序号；稳定ID是程序长期引用的身份。若删除P2后，原P3显示为P2，已有关系仍应指向原来的对象。把显示序号当主键，会让重新编号悄悄改变关系含义。

    同样，关系需要引用某个确定的命题版本。只保存“这份文书的P3”，却不保存它来自哪个版本，在回退重标后就无法重现旧结果。

    6.4 从分析类图走向设计类图 #

    分析类图先表达业务理解。设计类图进一步加入方法、接口、可见性、技术辅助类和依赖。例如概念“冻结命题版本”可以落实为领域对象，服务类负责协调事务，仓储接口负责读写。

    这不是把每个概念机械地变成一张表、一个Service和一个Controller。先看职责、变化和一致性要求，再决定代码中的映射。

    6.5 从用例名词中筛出核心概念 #

    “用户”“任务”“文书工作项”“指南版本”“原文版本”“切割版本”“轮次分配”“个人标注版本”“要素”“关系”“裁定记录”“冻结命题版本”“终稿快照”“练习”“练习尝试”“标准答案版本”都有明确业务意义。

    任务通常是一批材料与配置的组织单位，文书工作项维护单份文书的进度。不要把每一份文书都依附在一个会同时推进的全局stage上。个人标注版本表达某人在某轮的作答，提交快照表达一次确定交付，二者也不应混成一个共享数组。

    6.6 一组足够开始讨论的关联 #

    一个任务包含多个文书工作项；一个工作项绑定确定的原文与指南版本，并有多条轮次分配；一个分配连接用户、轮次与职责；一个工作项有多个人标注版本和裁定记录；一个冻结命题版本包含确定的要素集合；一个关系版本引用一个冻结命题版本，并包含多条关系。

    一个终稿快照绑定具体命题版本与关系结果；一个练习绑定教学材料与标准版本；一名学生可以有多个练习尝试。若允许一次尝试只针对一个练习，则尝试到练习是1，练习到尝试是0..*。其他多重性需按允许的草稿、空任务与发布规则确定。

    6.7 属性先表达业务含义 #

    概念关键属性示例为什么需要
    文书工作项ID、状态、当前有效基准每份文书独立推进
    轮次分配用户、轮次、职责、生效状态防止同角色跨文书越权
    原文版本内容、版本、指纹确定字符定位的依据
    要素稳定ID、原文区间、显示序号、类型防止重编号破坏引用
    个人版本所有人、轮次、基准版本、提交状态实现独立作答与复现
    关系稳定ID、类型、操作数引用支持嵌套与方向
    裁定记录对象、选用结果、理由、裁定者、依据说明结果怎么形成
    练习尝试学生、标准版本、提交与反馈允许重做并保留原口径

    6.8 分析图里先不要写满框架类 #

    这一阶段重点是业务概念与联系，通常不写Controller和SQL方法。后续设计会增加FreezeService、RelationRepository等实现协作对象，但不能让技术名词掩盖“什么数据是谁的、属于哪一版”这些核心问题。

    画完后用三个问题走查：某个学生尝试能否误连到正式终稿；某条关系能否找到原文与命题基准；某份个人作答能否明确归属于一个用户和轮次。答不出来，通常说明关联或版本概念不完整。

    本章产出：领域术语、概念类图、关键属性、多重性和约束说明。后续ERD与设计类图基于它发展，不能拿一张图替代所有层次。

    6.9 把多重性逐句读出来 #

    “任务1—工作项0..*”表示固定一个任务，允许有零个或多个工作项；固定一个工作项，它属于一个任务。如果发布时要求至少一份文书，应在发布约束中规定，不能让草稿阶段也被不必要地限制。

    “用户1—分配0..*”和“工作项1—分配0..*”共同表达多对多及其附加信息。分配还需有轮次和职责，所以它不仅是两条ID的连接。对同一工作项，命题标注与关系裁定是不同分配，权限不能只根据用户的全局角色推断。

    6.10 概念类图不要过早承诺存储细节 #

    概念上的“个人提交快照”可以通过不可变版本引用或单独副本实现；概念类图先确认其身份和关系，详细设计再选实现。反过来，如果分析里没有个人版本和冻结基准，数据库再精巧也难以凭空补出一致业务含义。

    7 系统顺序图 先约定黑箱行为

    7.1 系统顺序图把系统当黑箱 #

    系统顺序图（SSD）通常画参与者与一个“系统”生命线，按时间从上到下列出系统事件和返回。它回答“外部什么时候给系统什么请求，系统怎样响应”。不要在这张黑箱图里继续画Controller、数据库和内部服务。

    例如：裁定者发出 freezePropositions(workItemId)，系统返回 frozenVersionId 和可进入关系轮的状态。这是外部可观察的契约，不规定内部要调用多少个对象。

    7.2 UML常用元素 #

    生命线代表交互中的参与者或对象；时间向下流动。同步调用通常用实线和实心箭头，异步消息用开放箭头，返回常用虚线；图中应有清楚的图例。激活条表示执行中的控制。对象创建从创建消息处开始，终止叉号表示生命线真正结束，不是“这次操作做完了”。

    片段含义例子
    alt根据守卫条件选择互斥分支合法则保存，否则返回错误
    opt条件成立时可执行的一段用户调整布局时保存坐标
    loop满足条件时重复交互对每名被分配用户接收提交
    ref引用另一段已命名交互引用统一切割裁定流程

    loop 说明重复，不自动表示真实用户必须排队串行。多个标注员可能各自操作，图中需要表达个人版本隔离。返回箭头应回到直接调用者；通过多层处理的结果应沿协作链返回，避免图与职责分配矛盾。

    7.3 这张图只回答外部交互 #

    SD1的主角是命题标注员、命题裁定者、关系标注员和关系裁定者，系统本身是一条黑箱生命线。有输出权限的角色可以在末尾请求导出。不要在同一张SSD里再展开数据库、关系服务和渲染对象。

    7.4 按时间从上到下读完整主线 #

    第一，命题标注员打开被分配文书，系统返回原文、指南与当前权限。此时不能返回另一人尚未公开的答案，否则独立标注不成立。

    第二，分别提交切割，裁定者检查并确认统一切割版本。你可以用ref引用命名子交互，但应在正文或另一张图中说明子交互含什么；ref不是隐藏未定义业务的借口。

    第三，各人在统一切割上标类型与要素归属，保存个人草稿，提交时形成独立快照。直到当前轮次所需人员提交齐备，才进入命题待裁定。两个人是两个真实身份与版本，不是同一用户点击两次。

    第四，命题裁定者查看结果，处理分歧与遗漏，必要时反馈修改。确认完整后发出冻结请求，系统校验并返回冻结版本ID，开放关系轮。裁定者点击确认与系统生成快照，是不同责任。

    第五，关系标注员读取同一个冻结命题版本，分别完成并提交自己的关系结构。所需提交齐备后，关系裁定者处理分歧并核查完整图示，确认后生成终稿。

    第六，有输出职责的用户选择终稿导出。系统返回实际文件或文件获取信息，并保存导出记录。只弹“成功”没有文件，不满足这里的后置条件。

    7.5 loop alt和ref应放在哪里 #

    loop适合表达“每个被分配者分别提交”或“持续编辑直到提交”。守卫应能看懂，例如“仍有未完成提交的本轮人员”，不能只写一个无含义的i++。它不要求真实用户串行工作。

    alt适合“冻结条件满足/不满足”“允许导出/拒绝导出”等分支。冻结失败要返回缺失条件并保持状态；成功才生成版本并推进。若使用ref表示回退，必须有明确的发起者、条件、处理责任与结果。

    7.6 原型能帮助你发现哪些遗漏 #

    原型v3.0用S.stage、S.subProp、S.subRel及共享SEG、REL等变量演示流程，并提供“模拟另一名标注员提交”。这些设计便于展示门禁，但实际系统必须将状态按文书、身份和版本保存。

    原型submitCut()显示固定4.8%的提示，不能作为真正计算了一致性指标的证据。SD1应依据确认规则表达“计算/人工确认/阻止推进”等职责，不把固定演示值写成业务事实。

    7.7 这张图交前检查 #

    确认先有统一切割、再有类型标注；先有命题提交与裁定、再有冻结；先冻结、再关系；先完成关系裁定、再输出。确认失败不跳状态，其他人的作答不被泄露，每条消息都能在用例中找到依据。

    复述练习：不用术语，向室友解释为什么命题和关系不能让两个人从头各做各的再直接合并。

    参考说法

    两人可能把文本分成不同句段，连“P3指谁”都不一致。先统一命题边界和含义，再让他们基于同一版本标关系，最后比较的才是同一组对象之间的连接。

    7.8 从一句基本流提取系统事件 #

    “裁定者检查结果并请求冻结”可以提取为freezePropositions(workItemId, expectedRevision)。workItemId说明操作哪份文书；expectedRevision说明用户确认时看到哪次修订。调用者身份从认证会话取得，不应由用户随意填写一个actorId来冒充。

    系统成功返回snapshotId、state与revision，失败返回稳定错误及可恢复信息。SSD关注外部事件与响应，所以不在同图展开它使用悲观锁还是乐观锁；这些决定留到详细设计。

    7.9 怎样审查一次返回 #

    问“用户下一步能做什么”“界面怎样判断保存成功”“失败后原输入还在吗”。只返回一个true可能不足以帮助后续读取基准和应对版本变化；返回全部内部对象又可能泄露不该看到的数据。响应应围绕用例后置条件组织。

    8 状态建模 让阶段门禁可以执行

    8.1 状态图描述一个对象的生命周期 #

    顺序图关注一次交互，状态图关注一个业务对象经历哪些稳定状态。转换可写成“事件 [守卫] / 动作”。例如“请求冻结 [提交齐备且裁定完成] / 创建冻结版本”。状态是“待裁定”“已定稿”，按钮文字或页面名称不一定是状态。

    把某份文书的状态与整个批次任务分开。一个任务可能有100份文书，其中一份已定稿，另一份还在切割；一个全局stage变量无法真实表达这种情况。

    8.2 活动图和其他模型怎样配合 #

    活动图擅长工作流程、分支、并行与职责泳道；状态图擅长生命周期与允许操作；顺序图擅长消息与协作。它们从不同角度描述同一个系统，不应互相矛盾。

    检查一致性的办法很具体：用例写“冻结前拒绝”，状态图要没有非法写入转换，顺序图要有拒绝分支，后续代码和测试也要落实。模型价值在于暴露问题，不在图的数量。

    本章自测：一张顺序图同时画“标注员—系统—关系服务—数据库”，并把“系统”当黑箱，哪里有问题？

    展开答案

    抽象层次混在一起了。应拆成系统顺序图与详细顺序图，或明确这是内部设计图并直接使用承担边界职责的对象，而不是保留一个含义不清的黑箱系统。

    8.3 正式标注的六阶段主线 #

    创建任务→命题标注→命题裁定与冻结→关系标注→关系裁定与定稿→图示与结果输出

    这是原型v3.0与后续分析采用的主线。第二阶段内部还应理解为“独立切割 → 提交切割 → 裁定统一切割 → 独立类型标注与提交”，不能把进入第二阶段就理解为任何时候都能直接改标签。

    两名标注员分别交出自己的答案；命题裁定者处理差异、遗漏和明显错误，确认统一命题集并冻结；关系标注员基于该冻结集分别作答；关系裁定者检查完整关系与图示，形成终稿；输出从终稿生成文件。

    原始需求文档是“创建—标注—冲突解决—输出”四阶段。六阶段把“标注”与“冲突解决”按命题和关系展开。更新作业时，要同时改用例前置条件、状态模型和详细顺序图，不能只把流程图拆成六个框。

    8.4 回退应怎样理解 #

    原材料存在“流程不可逆”“输出后不可编辑”与后续“解冻生成新版本”的不同表述。一个可供确认的工程方案是：旧冻结版和终稿保持只读；有权用户提出修订；生成新命题版本；识别受影响关系并重新复核；生成新终稿。

    这样既能追溯旧结果，也能纠正错误。但“谁能申请、谁批准、哪些状态可发起、旧关系如何迁移”仍需要业务决定。不能仅把界面的stage减一，就宣称版本化回退已经实现。

    8.5 为一份文书建立清楚的状态机 #

    可以采用以下教学状态：草稿、切割中、切割待确认、类型标注中、命题待裁定、关系标注中、关系待裁定、已定稿。六个业务阶段可以把其中部分子状态合并展示；持久状态怎样细分是设计选择，必须能执行相同业务约束。

    当前状态事件守卫或检查动作与新状态
    草稿发布材料 指南 分配完整生成工作项，进入切割中
    切割中完成本轮切割提交所需独立提交齐备进入切割待确认
    切割待确认确认统一切割按确认口径审查完成绑定切割版本，开放类型标注
    类型标注中完成所需提交必填 覆盖与独立提交符合约定进入命题待裁定
    命题待裁定冻结裁定与完整性完成创建命题基准，进入关系标注中
    关系标注中完成所需提交同一有效基准且提交齐备进入关系待裁定
    关系待裁定确认定稿关系 引用 图示与遗漏检查完成创建终稿，进入已定稿

    守卫不满足时，不执行转换，也不产生半套动作。界面上的“待裁定”与后端值可以不同，但含义应一致。关系轮里保存一次草稿通常不是新的流程状态，只是当前个人版本修订发生变化。

    8.6 版本与状态是两条不同的轴 #

    状态回答现在允许做什么；版本回答数据是哪一次确定内容。PV-1和PV-2都可能曾经冻结，它们有不同身份与来源。工作项可以指向当前有效基准，旧基准仍作为历史存在。不要用一个stage整数同时替代流程、版本和历史。

    8.7 状态机如何暴露原型问题 #

    若冻结成功从阶段三进入阶段四，但解冻函数只允许阶段三执行，入口就可能不可达。先在状态转换表里明确“受控修订从哪些状态可申请、由谁批准、产生什么新版本”，再更新权限和页面。只放一个“回退”按钮不能补完这个契约。

    练习 任务有十份文书 其中一份冻结后是否整个任务都应进入关系轮

    除非业务明确要求全批次同步，否则应按文书工作项独立推进，任务展示汇总进度。全局一个stage会把不同文书错误地绑定到同一生命周期。

    教学模拟只检查下面选择的条件，不连接正式系统，也不写入数据。改变一个条件，再观察拒绝原因。

    9 详细顺序图 分配内部对象职责

    9.1 详细顺序图打开内部协作 #

    详细顺序图展示内部对象如何完成同一个场景。在分析表达中常用边界对象、控制对象和实体对象：边界接收与展示，控制协调一次用例，实体保存业务状态并承担相关业务规则。设计阶段还可加入仓储、外部接口等技术对象。

    例如“创建关系”可以分成：标注界面接收输入；关系控制检查当前文书、角色和版本；规则对象检查引用；标注版本保存关系；图示组件根据保存的结构生成显示。每条消息都意味着接收者承担相应职责，需要与类图保持一致。

    9.2 为什么要从SSD继续展开 #

    SSD说“系统接收关系并保存”，SD2需要解释系统内部谁完成检查和保存。案例分析采用标注交互、关系标注控制、标注版本、标注指南和论证图示等对象：它们是职责分配，不意味着必须创建完全同名的Java类。

    边界收集操作并展示结果；控制对象组织场景；版本对象提供状态与基准；指南对象提供结构约束；图示对象生成展示。落到设计后，还可以分出仓储和渲染适配器。

    9.3 第一步 明确请求到底包含什么 #

    教学示例输入包括workItemId、personalVersionId、basePropositionVersionId、关系类型与操作数。S、A、M通常有来源和目标，J、I有成员集合；操作数要说明它是命题还是关系。

    例如创建R4=A(P5,R3)，传入的两个引用应能区分element与relation，不能都用一个不带类型的数字。ID空间是否全局唯一、哪些对象可以作为各关系操作数，由数据契约规定。

    9.4 第二步 把校验分成几层 #

    先检查身份、工作项分配和轮次职责；再检查工作项处于可写关系阶段；再检查个人版本、冻结基准和当前有效版本一致；最后检查成员数量、重复成员、对象存在、命题资格、引用范围和嵌套循环。

    结构校验通过表示“这条数据可以被系统解释”，不表示“这条法律论证在语义上正确”。J是不是缺一不可、A到底攻击哪个对象，仍需要标注和裁定人员判断。

    循环引用特指递归对象结构，例如R1引用R2而R2又引用R1，会让展开结构无法结束。不要据此把所有命题图里的语义环路一概自动禁止；后者需要单独业务规则。

    9.5 第三步 保存与图示分开理解 #

    合法时先保存结构，返回稳定关系ID和结构修订号，然后根据这份结构生成图示。非法时不新增关系，返回具体错误且保留输入。若保存成功而图示失败，应明确“数据已保存，图示待刷新”，允许只重建展示，防止用户重复创建。

    列表与图示都要标明或内部绑定同一修订。否则列表是新关系，图示还是旧结构，用户会误以为数据丢了。是否异步渲染、怎样通知完成属于设计决定，应写进接口和交互说明。

    9.6 第四步 处理布局和依赖删除 #

    只移动节点就走opt保存布局坐标，关系类型、方向和成员不变。若修改成员或方向，需要重新走结构校验。

    删除R1前若R2引用它，应列出依赖。可以选择阻止删除，或者在明确确认后处理依赖；不能不告知就留下悬空引用。教学初版可先实现阻止并定位依赖，是否支持级联操作需业务确认。

    9.7 画图时常见的错误 #

    不要让界面直接读取数据库后决定能否写；不要在非法分支后仍画保存；不要所有返回都跨层直达用户；不要用销毁叉号表示一次渲染结束；不要把所有校验写成一句“检查合法”却无法解释检查对象。

    本章产出：一张职责清楚的详细顺序图、一组操作数与校验契约，以及成功、非法、渲染失败、依赖删除等场景说明。

    9.8 SD3 创建任务怎样逐步展开 #

    有创建职责的用户请求建立草稿，系统先检查权限再生成草稿ID。任务集合或仓储已存在时，由它创建新任务记录；不要因为图中出现“创建任务”，就把整个集合对象画成刚刚诞生。

    上传指南后形成候选版本，返回摘要与错误。只有候选有效且创建者核对确认时，才绑定到任务。用loop表达未绑定且未取消时的重试，用opt表达“有效且确认”时绑定，比无条件写入更准确。

    随后导入文书，确认裁判理由范围和原文版本，分别配置命题轮与关系轮标注员及裁定职责。发布时检查材料、指南和分配是否完整；成功才开放可领取工作项，失败保留草稿并说明缺什么。

    9.9 发布检查不能只看总人数 #

    总共分配4个人，但全部在命题轮，关系轮仍然没有人员。应分别检查两轮要求。修订分析把指南的双人独立标注落实到两轮配置，这是一个可追溯的建模解释；具体兼任、回避、特殊人数和后续替换规则应形成确认记录。

    取消创建不应产生可领取任务。草稿是否保留、临时上传多久清理、发布后新增文书怎样继承指南等，不必在顺序图上挤满文字，但应在场景说明或业务规则中有答案。

    9.10 让每条内部消息都有接收者职责 #

    把“校验并保存”拆开看：应用服务接收用例请求；工作项提供当前状态与有效基准；分配或权限组件确认当前人的职责；关系验证器检查结构；仓储执行受控保存；图示组件生成展示。消息接收者的类或接口，应在设计模型中有相应能力。

    不要为了让图短，就让“标注版本”凭空知道当前登录用户、教师答案策略和网络响应格式。掌握业务数据不意味着应该承担所有技术责任。反过来，应用服务也不应重新实现所有领域规则。

    9.11 详细顺序图怎样表达一个失败分支 #

    先画读取和校验，再用alt分出“合法”“非法”；合法分支才包含保存消息；非法分支返回具体错误。若图把保存放在alt之后，所有分支都会继续执行保存，就与正文“非法不写入”矛盾。

    图示失败属于保存之后的另一种结果，需要说明关系是否已提交。不要用一个catch把业务保存失败与展示失败混为同一种“请重试”，否则客户端可能重复创建关系。

    10 教学支持 标准 练习 尝试与反馈

    10.1 为什么有这么多角色 #

    任务创建者负责材料、指南与分配；命题标注员负责切割与类型；命题裁定者确认统一命题基准；关系标注员建立论证关系；关系裁定者确认完整结构；教师发布标准和练习；学生独立作答。

    角色描述职责，同一个真实用户可以承担多个角色，但是否允许同一人在同一文书上既标注又裁定，需要回避规则。界面有角色切换不等于服务端已经授权，任务分配和当前阶段也必须同时成立。

    10.2 教学练习是另一条业务链 #

    教师在教学材料上建立标准要素、关系和图示，发布绑定材料、指南和标准版本的练习；学生在个人尝试中作答；系统按策略比较并给出反馈；允许重做时保留多次尝试。

    仅命题练习在命题反馈后结束；仅关系练习可使用教师提供的统一命题集；命题加关系练习需要先决定后半程使用哪份命题基准。标准答案何时可见、提交后能否重做、是否允许学生修改副本，都是需要教师策略的内容。

    正式裁定是在没有预设正确答案的新文书上形成结果，教学反馈是在已绑定标准下比较学生作答。两者可以共享编辑器、规则和图示代码，但入口、数据范围与写入权限需要区分。

    10.3 SD4 为什么单独表示教学 #

    修订版增加独立教学系统顺序图，使教师和学生目标清楚。教师建立标准，发布练习；学生领取个人尝试，完成命题或关系标注；系统依据绑定标准对齐和比对，按策略开放反馈；教师查看学情。

    独立“系统黑箱”是为了说明教学业务边界，不自动表示必须单独部署。实现上可以共用规则、编辑器和图示组件，同时通过模块、查询范围和权限隔离数据。

    10.4 教学流程最容易漏的三个条件 #

    标准必须匹配材料。不能因为系统里有任意标准答案就允许发布；必须绑定同一材料、指南和适用范围。关系练习必须有命题基准。命题边界不一致时，先对齐，不要逐编号硬比。反馈要有开放策略。练习前查看全部答案与独立作答目标可能冲突，需要教师决定开放时间和范围。

    学生修改原文时，应限于明确允许的个人副本，并重新检查定位与对齐；不能改教师原文后继续用旧索引。标准更新时建立新版本，已有尝试和反馈继续绑定原口径，重做建立新尝试而非覆盖旧记录。

    10.5 三张图还是四张图 #

    第二次作业原文是SD1、SD2、SD3三个主要场景，v3.0修订版又加入SD4教学支持。讲解会覆盖四个场景；提交时采用几个图、哪些属于正式要求，应对应当前任务书。增加教学图是为把独立模式解释完整，不是本讲义替老师新增必交数量。

    10.6 练习比对需要先对齐对象 #

    假设标准有区间[0,10)、[10,20)，学生有[0,20)。标准的P2与学生的P2根本不存在直接对应关系。系统应先报告边界差异，再根据确定策略进行匹配；没有匹配的元素单独列为未对齐，不用相同显示序号硬配。

    对齐后，再比较要素类型。关系比较要把操作数映射到相同基准，并区分类型、方向、成员集合与嵌套结构。对J和I这类集合结构，成员顺序是否影响比较需按指南和规范化约定处理；对S、A、M，来源目标不能交换。

    10.7 不要过早把反馈压成一个总分 #

    可以先展示可解释的差异：未对齐区间、类型不同、关系缺失或多余、方向不同、嵌套对象不同。若需要综合分数，要确定各类权重、部分正确、边界差异传播与重复计错规则，并由教师确认。

    两人正式标注的一致性、学生与教师标准的匹配程度、模型的预测指标，是不同评价问题。它们都叫“准确率”会让结果无法解释。

    10.8 三种练习的基准策略 #

    初学关系时，提供统一的教师命题集，能把学习重点放在关系。综合练习若保留学生自己的命题集，就必须处理到标准的对齐。命题练习后是否直接给标准命题集进入关系轮，会改变教学反馈目的，发布时要说明，而不是由程序临时决定。

    11 结构化分析 ERD DFD与数据字典

    11.1 为什么还要学另一套分析方法 #

    面向对象分析围绕业务对象、状态和协作组织理解；结构化分析围绕数据如何进入系统、经过哪些处理、保存到哪里组织理解。二者可以对同一需求提供补充视角。除非任务书要求，不必为了显得完整把所有图重复画一套。

    结构化分析常用实体关系图（ERD）描述数据，数据流图（DFD）描述处理，数据字典统一数据定义，决策表或决策树表达复杂规则。

    11.2 DFD的四种元素 #

    外部实体是系统边界外的数据来源或接收者；处理把输入数据转换成输出数据；数据流说明流动的数据是什么；数据存储保存后续还会使用的数据。处理名称一般用动宾短语，数据流一般用名词。

    以关系提交为例：外部实体“关系标注员”提供“关系提交数据”，处理“校验并提交关系”读取“冻结命题数据”和“任务分配数据”，写入“个人关系提交库”，输出“提交结果”。图上不需要画“用户先点哪个按钮”。DFD不是控制流程图。

    不能把外部实体直接连到数据存储来代替系统处理，也不能用存储到存储的箭头跳过处理。处理只有输入没有有意义输出，可能是“黑洞”；只有输出没有合理输入，可能是“奇迹”；输入不足以产生输出，是“灰洞”。

    11.3 分层与平衡 #

    上下文图把整个系统视为一个处理，展示边界外的交互；再分解为较大处理，逐层细化。不同教材对“第0层”的命名可能不同，读图时先说明自己的层级约定。

    父图的某处理被展开为子图后，跨边界的输入输出应保持平衡。若父图只有“关系数据”输入，子图却凭空出现一份外部标准答案，应检查是否漏掉了边界数据流。

    11.4 数据字典 决策表和ERD #

    数据字典要让“关系提交数据”有确定含义，例如由工作项ID、个人版本ID、命题基准版本ID、关系集合组成；关系集合中的引用需明确对象类型和ID。它不能只解释名称，还要说明结构、类型、取值、可空性与约束。

    决策表把条件组合与动作对应起来，适合“有权限、阶段正确、版本有效”共同决定能否保存的规则。决策树适合按判断路径阅读。组合很多时可以先按优先级约定错误处理，避免漏掉规则或让不同实现返回互相矛盾的结果。

    ERD表示实体、属性与联系。例如“用户—分配—文书工作项”，分配连接用户、文书与轮次。概念ERD尚不等于最终表结构；逻辑设计再决定主外键、关联表、约束与索引。

    11.5 先画数据而非直接写建表语句 #

    概念ERD先确认用户、文书、任务、分配、版本和关系的联系。用户与工作项通过轮次分配关联；冻结命题与关系版本通过基准引用关联；练习与标准通过发布绑定关联。每条联系都应解释“一个对象可关联几个，能否暂时没有”。

    “一份文书只能有一份标注”明显不够，因为存在多人、轮次、草稿和历史。可以说“一次个人作答版本属于一个人和一个工作项”，再用版本与提交关联表达历史。

    11.6 用DFD检查输入输出是否完整 #

    上下文层展示创建者、标注员、裁定者、教师和学生与系统交换的数据。展开时可分为任务配置、个人标注、裁定版本、教学练习和结果输出等处理。

    “生成终稿导出”需要确定终稿快照、指南版本、原文和关系结构，输出文件及导出记录。若图中只有“用户点击导出”而没有所需数据来源，就还没有把处理分析清楚。

    数据存储要经处理读写；DFD箭头写“导出请求”“终稿数据”，不要写“先做”“然后”。层次分解时检查父处理边界输入输出与子图一致。

    11.7 数据字典至少统一这些对象 #

    原文版本要定义字符编码、换行与偏移基准；要素要定义稳定ID、范围、类型；关系要定义有方向操作数和集合操作数；提交要定义身份、轮次、版本与状态；终稿要定义所绑定快照；练习反馈要定义对齐、标签与关系差异。

    例如原文范围可以采用“从0开始、左闭右开”的区间约定，但还需说明偏移单位是Unicode码点还是UTF-16码元。JavaScript字符串位置与Python处理中文扩展字符、表情时可能不同，不能只写“字符索引”就认为一致。换行与规范化也必须在生成版本时固定。

    11.8 一个最小数据流图样例 #

    下面只展示“提交关系”的数据流。箭头写的是数据内容，不表示用户界面的点击先后；权限、阶段与基准检查在处理中使用相关存储数据。

    可以再把“校验并提交”分解为读分配与状态、检查结构、写提交快照、组织提交结果。但分解图对外仍应接收相同关系提交数据、输出相同提交结果，不能偷偷增加父图没有的外部输入。

    11.9 从ERD走到关系表的一次转换 #

    用户与工作项的多对多，通过assignment关联表展开，外加round和duty。一个关系版本有多条关系，可在relation中保存version_id；一条关系有多个带槽位的操作数，可用relation_operand保存。这样“成员”是多行数据，不需要把E1,E2,E3拼在一个逗号字符串里。

    这只是逻辑结构起点。之后仍需决定多态引用怎样约束、操作数唯一性如何定义、关系循环在哪一层检查，以及如何防止跨工作项连接。

    12 需求规格 评审 验收与基线

    12.1 SRS要能支撑设计和验收 #

    SRS是软件需求规格说明书。它通常包含目的和范围、术语、总体描述、用户和外部接口、功能需求、质量需求、约束、业务规则、模型、验收和追踪。课程文件引用某个模板时，以该任务书要求为准；模板提供结构，不能代替真实需求内容。

    每条重要需求最好有稳定编号。一个可用的记录是：“FR-REL-01；来源为已确认业务规则；关系标注员仅能在关系轮向自己的有效版本添加关系；引用的命题基准必须是本工作项当前有效的冻结版本；失败不新增关系；验收见T-REL-01至T-REL-04。”

    “实现语言用Java”属于设计或技术约束的内容；“关系必须有稳定引用”是对可重现行为的要求。需求允许出现必要的数据约定，但不要把所有内部类和算法先写死。

    12.2 评审不仅检查错别字 #

    先检查完整性：成功、失败、边界、权限、并发和恢复是否考虑到了。再检查一致性：原型、用例、状态、术语和字段是否相互吻合。最后检查可验证性和可行性：怎么证明符合要求，团队是否能在约束内做到。

    可以组织场景走查：请标注员实际从领取任务走到提交，再让裁定者走到冻结。每遇到“这里应该怎样”就记录问题；未决定的内容用明确的待决策状态管理，不能靠开发者各自理解。

    12.3 需求追踪把产物连起来 #

    追踪链可以是“来源 → 需求 → 用例 → 分析与设计 → 代码 → 测试”。它不一定是一张巨大表格，但必须能回答：需求有没有实现；这段代码为什么存在；需求改了影响哪里；测试覆盖了哪些要求。

    例如改变“冻结前置条件”时，至少要检查用例、状态转换、冻结服务、事务条件、接口错误和回归测试。只更新Word标题上的版本号，不等于完成变更。

    12.4 一个可靠的变更过程 #

    记录变更原因和来源；分析影响与成本；由有权决定的人确定范围；修改需求、模型与实现；执行相关验证；更新基线与记录。小团队不需要复杂审批仪式，但必须知道谁决定、改了什么以及验证结果。

    “冻结”并不表示永远不能变化，而是不能无控制地覆盖。业务版本与工程基线都可以通过明确的新版本演化，并保留旧依据。

    12.5 写成SRS的组织方式 #

    可按“引言与范围—术语与角色—业务流程—功能需求—业务规则与数据—质量与约束—接口—分析模型—验收与追踪—待决策事项”组织。功能需求用稳定编号关联用例与图，而不是把几张图截图贴进去就结束。

    质量要求不要复制CampusHub的两秒、三步等指标。本系统的8至10页文书还需换算为实际字符、要素、关系和并发规模，再确定可测目标。扫描件是否OCR、支持哪些导出格式、浏览器与部署环境，也应明确列入范围。

    12.6 可以立即使用的需求片段 #

    教学示例FR-REL-02：系统应拒绝引用另一工作项或无效命题版本的关系请求；拒绝后个人关系版本不产生新增记录。FR-TEACH-01：学生提交只保存到其练习尝试，不改变正式文书版本。FR-EXPORT-01：导出应从同一终稿快照生成，并包含关联版本信息。

    这些条目应补齐来源、优先级、状态与验收，再进入你的SRS。还应保留前面的待确认决策，不能把教学示例全部改成“用户已经确认”。

    12.7 把质量需求写成一个六要素场景 #

    以导出为例：刺激来源是有输出职责的用户；刺激是导出指定终稿；环境是该终稿已确定且系统处于正常负载；对象是导出服务及其数据源；响应是从同一快照产生可读取文件并记录来源；响应度量包括文件内容一致、可解析、元数据齐全和约定时间。

    时间阈值先标待测待定，不从别的项目抄一个两秒。先固定样本规模与环境做基线测量，再与需求方约定目标。质量目标需要付出设计与验证成本，不能只出现在文档开头的口号中。

    12.8 一条SRS记录的完整字段 #

    需求编号、标题、业务描述、来源、确认状态、优先级、前置与触发、输入输出、失败保证、关联用例、验收标准和变更记录。不必每条都用大表格铺开；字段齐全、能找到信息即可。

    例如状态约束可以在业务规则表中集中定义，再由多个功能需求引用，避免四个页面各写一套不同的冻结条件。复用的是同一条知识，不是把模糊句子复制到多个章节。

    资料对应 第14章需求文档 02 05需求文档化与验证。

    13 体系结构 模块 接口与设计取舍

    13.1 先理解结构中的三个要素 #

    组件承担职责，连接器说明组件怎样交互，约束规定允许的组合与依赖。模块名字的列表还不是完整架构；需要说明谁调用谁、传什么、怎样处理失败、部署在哪里。

    架构设计从关键功能、质量属性和约束出发。比如“多人独立提交”要求数据隔离；“冻结后可重现”要求版本化；“图示刷新失败不丢标注”要求把业务保存与展示计算的结果区分开。

    质量属性应写成具体场景：发生什么刺激、处于什么环境、作用于哪个对象、系统怎样响应、如何测量。只在图旁写“高可用、高性能、可扩展”，不能证明设计满足这些目标。

    13.2 读懂常见风格的取舍 #

    风格核心组织方式适合与代价
    分层展示、业务、数据等职责分层便于分工与替换；跨层限制和数据转换会增加成本
    客户端服务器客户端发请求，服务器提供能力适合Web交互；需处理网络失败和状态一致性
    MVC模型、视图、控制职责分离支持交互和多视图；具体框架对三者边界有差别
    管道过滤器数据依次经过独立转换步骤适合解析、清洗、转换；交互与共享状态不总容易表达
    事件驱动组件发布和处理事件减少直接依赖；调用链追踪、重复消息与时序更复杂
    主程序子程序主程序组织调用子程序简单直接；共享数据和集中控制可能增加耦合
    面向对象对象通过接口协作便于封装变化；划分不当仍会形成复杂依赖
    微服务多个可独立部署的服务协作支持独立演化；引入通信、数据一致性与运维成本

    这些风格可以组合。一个系统可以总体采用客户端服务器，服务端采用分层，展示端采用MVC。高并发不必然要求微服务；先找实际瓶颈和团队约束，再决定是否需要拆分。

    严格分层限制只能访问相邻下层，松散分层允许按约定跨层访问。这里说的是逻辑依赖。三个逻辑层可以在同一服务端进程中运行，也可以分布在不同部署节点；“三层”不等于“三台服务器”。

    13.3 从需求到架构的七步 #

    先识别关键需求；选择合适风格；划分子系统和模块；设计接口；决定物理部署；验证是否满足需求；组织评审并改进。逻辑设计往往需要多次调整，不能仅按网页菜单分包。

    标注系统的一个教学方案是：浏览器工作台通过HTTP调用服务端；服务端包含任务、标注、裁定、教学、导出模块；共享规则与图示能力；通过数据访问层保存版本和记录。教学独立入口与数据范围可以在同一服务端实现，不自动要求两个微服务。

    接口至少要说明操作、输入、输出、前后条件、错误、权限、版本与重试语义。远程接口不是写个方法名就结束，还要考虑网络不可靠和重复请求。

    13.4 多视图描述不同问题 #

    4+1中，逻辑视图描述主要对象与职责；开发视图描述代码模块和包；进程视图描述运行时并发与通信；物理视图描述部署节点；“+1”用典型用例串联并验证其他视图。

    C4从系统上下文、容器、组件、代码逐级放大。C4的“容器”指可运行应用或数据存储等单元，不专指Docker容器。C4与4+1是不同组织方法，不是逐项一一对应。

    包设计还要注意变化与依赖：一起变化的类适合靠近；共同复用的类适合聚集；避免循环依赖；依赖尽量指向稳定抽象。画包图时要说明箭头是编译依赖、运行调用还是数据流，不能用一根箭头同时含混表达所有关系。

    13.5 用ADR记录取舍 #

    架构决策记录（ADR）保留背景、选项、决定、理由和后果。例如“图示同步生成还是异步生成”：同步流程简单，但大图可能拖慢响应；异步需要任务状态、轮询或通知。决定以后还应记录条件，规模变化时可以重新评估。

    验证架构可以用场景走查、风险原型、接口集成测试和结构检查。自顶向下集成常需要桩代替下层，自底向上集成常需要驱动代替上层；不要等全部模块写完才一次性拼装。

    13.6 一个适合讲解的初始方案 #

    本讲义采用“浏览器前端＋一个模块化分层服务端＋数据库”作为教学方案。它让你先把复杂性集中在真实业务上：多人隔离、两轮流程、嵌套、版本与追溯。是否实际采用，还要结合现有项目框架和任务书。

    浏览器负责工作台和反馈；Controller接收请求与转换参数；应用服务协调任务、标注、裁定、教学和导出；领域规则保护状态与引用；仓储或DAO访问数据库；文件存储保留原始材料与导出产物。

    13.7 模块怎样分才有业务含义 #

    任务模块管理文书、指南绑定和分配；标注模块保存个人作答与提交；裁定和流程模块维护检查、冻结、定稿与修订；教学模块管理标准、练习、尝试和反馈；导出模块读取终稿生成文件。

    共享规则校验与图示能力可以被正式和教学调用，但调用者要提供明确上下文，不能自动把教学保存写进正式库。权限、错误、审计和事务是跨模块关注点，也需要明确责任。

    13.8 依赖方向与运行拓扑要分开画 #

    包图说明源码和模块依赖；部署图说明浏览器、应用服务、数据库与文件存储在哪里运行，通过什么网络连接。Repository接口与实现可以分离，应用服务依赖抽象，具体实现由装配注入。

    浏览器不能直接拿数据库密码读写正式表。也不要把“数据库有外键”画成浏览器与数据库之间的调用。一个服务端进程里有多层，不妨碍它具有清楚的逻辑分层。

    13.9 用三个ADR证明你做过判断 #

    第一，为什么先采用一个模块化服务端：记录团队与部署约束、单体与多服务的选项及后果。第二，为什么冻结产生不可变快照：解释多人比较与重现需要，说明存储与迁移代价。第三，图示为何与保存结果分开：解释展示失败的恢复和用户反馈。

    每个ADR要写选择条件和代价。不能只说“便于维护、扩展性好”，而要讲具体哪种变化被隔离、增加了哪些实现成本。

    13.10 早期怎样验证架构 #

    先用一份文书让页面、服务端和数据库真正连通；验证两个账号的草稿隔离；再验证一次冻结和一次嵌套关系；最后验证教学和正式数据不会串写。通过小范围贯通验证关键风险，再扩展功能范围。

    13.11 用一次请求同时检查不同架构视图 #

    在逻辑视图中，冻结涉及工作项、提交、裁定与快照；在开发视图中，对应流程、标注和存储模块；在进程视图中，考虑同时请求和后台渲染；在物理视图中，标明浏览器、应用服务、数据库与文件位置；用例场景把它们串起来。

    如果部署图中有消息队列，进程视图就要说明谁生产、谁消费、失败怎样处理。若只是一个同步服务，就不必为了“架构完整”添加并不使用的中间件。

    13.12 用变化场景验证模块边界 #

    场景一：导出从JSON增加SVG，主要影响格式与文件生成，不应重写命题裁定。场景二：增加新的图布局算法，主要影响布局实现，不应改变关系真值或引用。场景三：教学标准更新，旧尝试应保持原标准口径，影响标准版本与反馈绑定，不应覆盖正式终稿。

    变化实际涉及多个模块并不一定是错误；关键是依赖有依据、影响可解释，而不是每个新需求都要求修改一切。

    14 交互设计 让保存 提交 冻结各有含义

    14.1 可用性有具体的任务情境 #

    可用性关注特定用户在特定情境下，能否有效、有效率且满意地完成任务。它不等于界面漂亮。标注员能否准确选中文本、看清当前版本、恢复未提交草稿，都直接影响任务成功。

    用户有自己的精神模型：他认为点击“保存”只是存草稿，开发者却把它实现为“提交并锁定”，就会出现理解差异。按钮名称、反馈和真实状态应匹配用户预期。

    14.2 六个可直接检查的原则 #

    系统状态可见。显示当前文书、角色、轮次、冻结版本、保存情况，让用户知道自己在哪里。语言和业务一致。不要让用户猜“PR-01”和“RV-02”的含义，必要时同时展示中文说明。

    一致性。同一种操作在不同页面使用相同名称。及时反馈。保存后说明保存的是草稿还是提交快照；图示失败时不要把已保存的数据也说成失败。

    防错与恢复。冻结前列出条件与影响；删除被引用关系前展示依赖；网络失败保留输入。降低记忆负担。把相关原文、要素和图示联动展示，避免用户在多个页面记住编号再回来。

    14.3 原型怎样评估 #

    让真实用户执行任务，例如“找到未完成切割的文书并提交”“判断为什么不能冻结”“在图中找到反对关系的目标”。观察完成情况、错误、耗时和求助点，再问原因。不要只收集“看着不错”的评价。

    交互设计还应考虑差异：熟练用户需要快捷操作，新用户需要解释；颜色需要文字或符号辅助；拖拽操作应有可点击或键盘替代。关键状态不能只靠颜色区分，焦点要可见，缩放后内容仍应可读。

    14.4 布局动作与业务动作要分开 #

    拖动节点可能是调整位置，也可能是建立关系。界面需要明确模式和反馈。位置改变通常只更新坐标；改变关系类型、方向或成员会修改业务结构，需要重新校验。将两者混用会让用户在整理版面时意外改掉论证含义。

    14.5 从现有布局理解工作任务 #

    原型把原文、要素列表、操作与图示放在工作台中，这有助于对照阅读。继续设计时要保证显示全文的要求、选区定位、当前角色与轮次、草稿和提交状态都清楚。

    不要让一个按钮叫“保存”，实际却推进到下一轮。现有原型saveWork()按阶段调用submitRound()，说明演示中保存和提交有所混合；真实系统应明确区分“保存草稿”“提交本轮”“确认冻结”“确认定稿”。

    14.6 门禁要解释为什么不能做 #

    关系轮未开时，显示“命题集尚未冻结”；提交不齐时，显示缺哪项；用户无分配时，说明此文书不在其可操作范围。界面禁用操作并给出下一步，比只有一个灰色按钮更容易理解。

    页面读到阶段四后，其他人可能已发起受控修订。此时提交失败要提示版本已变化、保留输入并给出重新关联方式，不能简单让用户重新输入所有关系。

    14.7 原型需要补足的真实行为 #

    演示行为实现时需要补什么验收证据
    模拟另一人提交真实账号与个人版本隔离两个会话分别提交，各自记录可查
    固定切割通过提示确认的算法或人工流程变化输入产生相应结果与记录
    解冻提示生成新版本新旧版本、权限、依赖复核旧版可查，新版ID不同，影响可追踪
    导出成功提示实际文件生成与获取文件可打开，内容与终稿一致
    标准发布或学生比对演示标准绑定、个人尝试、答案策略不同材料不会错配，答案按策略开放

    14.8 原型中的具体规则也要核对 #

    v3.0提示M发生在一般与个别之间，但未完整表达单向保存约束；提示J只发生在同类之间，比指南“任何命题要素之间”更严格。导入页仍有针对旧GM-C的冲突提示，不能让系统对已采用SM-C的新指南也假报冲突。

    冻结后进入阶段四，而unfreezeProp()仍通过阶段三的canJudgeP()检查；这使解冻入口的可达性与权限需要重新设计。输出页还保留不可回退文字，也应与批准的修订策略统一。

    这些都是把原型用于需求评审的好例子：发现问题后，写成规则与场景，更新所有相关产物，不只是修一句提示语。

    本章产出：明确的交互状态、保存与提交区分、错误与恢复、布局与结构操作区分，以及用真实任务开展的评估记录。

    14.9 把关键反馈写成用户能采取行动的话 #

    “冻结失败”不如“尚有1名命题标注员未提交，当前裁定结果已保留，请等待提交后再确认”。“版本错误”不如“命题基准已更新，当前输入已保留，请重新读取并复核引用”。前提是系统确实做到了保留，而非先写一句好听的提示。

    保存草稿显示保存范围和时间；提交显示本轮锁定或后续修改策略；冻结显示基准版本；定稿显示终稿版本。用户通过这些反馈形成正确的精神模型，减少把不同动作当成同一件事。

    14.10 破坏性动作先解释影响 #

    删除被引用关系时，显示会受影响的外层关系。受控修订命题时，说明旧版本会保留、哪些关系要重新复核，以及当前账号是否有批准权限。拖动节点仅调整布局时，不要弹出“关系已修改”这种含混提示。

    15 详细设计 模块化 信息隐藏与模式

    15.1 从大模块走向可实现的协作 #

    体系结构确定任务、关系、教学等模块后，详细设计继续明确类、方法、接口、数据结构和算法。输入来自需求、分析模型与架构约束，输出包括设计类图、详细顺序图、数据与接口细节，以及验证这些协作的测试设计。

    “职责”包括知道什么和做什么。“知道”是维护什么信息及关系，“做”是计算、创建、检查或协调什么行为。设计时同时考虑静态结构与动态协作：先有类没有场景，容易漏方法；先画消息没有职责，又容易让某个控制类做所有事情。

    15.2 GRASP给职责分配提供线索 #

    信息专家原则：把职责分给拥有所需信息的对象。例如标注版本最清楚自己引用哪个命题基准，适合提供版本一致性判断。创建者原则：让包含、聚合、使用或掌握初始化信息的对象负责创建相关对象。

    控制器原则：由适当的非界面对象接收系统事件，协调一次用例。低耦合和高内聚原则帮助比较不同分配：尽量减少不必要依赖，让每个对象的职责围绕清楚的目的。

    例如FreezeService协调读取工作项、检查提交、生成快照与保存状态；领域对象维护“什么状态可冻结”的约束；仓储接口负责获取和保存。把所有规则写进按钮点击函数，会让其他入口无法可靠复用。

    15.3 集中 委托与分散控制 #

    集中控制由一个对象主导，大流程易追踪，但容易形成过大的控制类。委托控制让协调对象把局部责任交给信息更合适的对象。分散控制使多个对象各自承担局部行为，但整体流程可能更难阅读。

    选择看业务复杂度与团队理解成本。不能因为“面向对象”就追求最大限度分散，也不能把“有Service”当作设计已经合理。若一个类同时处理授权、切割、裁定、导出和布局，它的变化原因太多。

    15.4 契约与一致性边界 #

    方法契约包含前置条件、后置条件和对象不变式。不变式是在允许操作前后都应成立的约束，例如“每条关系的引用都存在于同一有效版本范围”。

    一次冻结如果同时创建快照和推进状态，这两项需要共同成功或共同失败，通常应在事务边界内协调。只把方法名写成freeze，并不会自动获得原子性。还要考虑两个用户同时请求、旧页面提交、网络重试等情况。

    15.5 高内聚 低耦合到底在说什么 #

    内聚关注一个模块内部的职责是否紧密相关；耦合关注模块之间的依赖强度。关系规则校验放在一起通常有较高内聚；规则校验还顺手发送教师统计邮件，就混入了别的职责。

    依赖不仅是import或调用次数。共享全局变量、依赖别人的内部字段、传入控制标志要求对方切换行为、依赖过多数据，都可能增加耦合。接口少也不一定低耦合，一个暴露全部内部状态的大接口仍可能非常脆弱。

    15.6 信息隐藏把可能变化的决定关在边界内 #

    封装提供把状态与行为组织起来及控制访问的机制；信息隐藏进一步强调：其他模块不应依赖那些容易变化的设计决定。例如导出模块只调用图示接口，不应知道布局算法的内部节点数组怎样存储。

    即使字段都设为private，若通过getAllData()把可变内部集合直接交出去，其他对象仍能绕过约束。应暴露有业务意义的操作和受控结果，而不是用getter/setter把所有内部细节重新公开。

    15.7 常用原则要能联系具体问题 #

    原则可以怎样理解标注系统中的应用
    单一职责 SRP一个模块围绕相关变化原因组织导出格式变化不应迫使冻结逻辑变化
    开闭原则 OCP通过扩展处理已识别的变化新增导出格式时增加实现，而非重写所有调用者
    依赖倒置 DIP高层政策与细节依赖适当抽象冻结服务依赖仓储接口，不直接拼接SQL
    接口隔离 ISP使用者只依赖所需能力学生练习接口不包含正式任务裁定操作
    里氏替换 LSP子类型遵守上层契约替换实现后仍满足规定的成功、失败和状态保证
    迪米特法则 LoD减少跨越对象内部关系的消息链不让界面一路取任务再取版本再直接改其内部列表
    DRY同一知识不要在多处独立维护同一关系合法性规则不要各页面各写一份

    依赖注入DI是把依赖从外部提供给对象的装配方式；依赖倒置DIP是设计上的依赖原则。用了注入框架不等于自动符合DIP。

    LSP不只是“语法上能向上转型”。子类型不能要求更强的前置条件、不能提供更弱的后置保证，还应维护不变式。仅为复用列表代码而让栈继承一个允许任意插入删除的集合，可能暴露不符合栈语义的操作；组合通常更合适。

    本章自测：把所有方法都放进CommonUtil，是否实现了代码复用和高内聚？

    展开答案

    未必。相同的代码可以复用，但无关职责集中在一个工具类会形成杂物箱。应按稳定职责和变化原因划分。DRY关注重复知识，也不能作为把所有相似代码强行抽象的理由。

    15.8 模式解决反复出现的设计问题 #

    模式包含问题情境、结构、适用条件与后果。学习时要先说“哪里会变，当前设计为什么难改”，再选择模式。没有变化需求时增加很多抽象类，反而让系统难读。

    策略模式把可替换算法放到共同接口后面。例如图示布局有不同算法，调用者只依赖LayoutStrategy；切换算法不改变冻结和裁定流程。若目前只有一个简单实现，可以先保持结构清楚，再根据真实变化抽取。

    抽象工厂提供一组相互配套的对象。例如一种已确定的指南图元方案同时需要命题图元、支持图元与匹配图元，可由同一工厂产出，避免混入其他方案。它与“仅创建一个对象”的简单工厂概念不同。

    15.9 另外几个课程常见模式 #

    单件或单例模式限制某类在某个运行范围内只有一个实例，并提供访问方式。它可能带来全局状态、测试困难与并发问题；多进程部署时，每个进程的单例也不自动成为整个分布式系统唯一实例。

    迭代器提供统一遍历方式，隐藏集合内部组织。观察者让对象变化后通知订阅者，适合列表和图示同步，但要处理通知时机、解除订阅和循环更新。适配器把已有接口转换成使用者期望的接口，可隔离文件解析库或图示库的接口差异。

    模式之间可以配合，但每一种都应有明确理由。考试或作业中若要求用模式改写，先指出旧设计的具体问题，再给出接口与协作，最后解释新方案的代价，不能只画一个模式标准图。

    15.10 设计类与原则怎样对应 #

    FreezeService协调冻结事务；WorkItem维护允许的状态转换；SubmissionRepository读取所需提交；SnapshotRepository保存只读结果；RelationValidator校验结构；GraphRenderer将结构转为展示；ExportService读取同一终稿并组织输出。

    这套职责体现高内聚与信息隐藏。新增SVG导出不应迫使冻结服务变化；修改布局算法不应改变关系存储。可通过ExportFormatter、LayoutStrategy等接口隔离真实变化点，不必为尚不存在的需求预先制造大量空接口。

    本章产出：设计类与协作、表结构或存储设计、约束、事务、版本与并发策略，以及对应验证方法。

    15.11 从一个过大的控制器开始重构 #

    假设AnnotationController同时解析指南、检查分配、切割文本、冻结命题、渲染图和导出文件。问题不是行数本身，而是多个变化原因挤在同一处：指南格式、业务规则、布局和文件输出互相影响。

    先提取清楚职责：GuideParser返回候选配置；WorkflowService协调状态与版本；RelationValidator检查结构；GraphRenderer生成展示；ExportFormatter生成特定格式。Controller只把请求交给用例并映射响应。提取后运行回归，确保外部行为未改变。

    15.12 抽象应该围绕真实变化 #

    如果两个导出格式共有“读取终稿”却有不同的编码方式，可以共享数据读取并替换格式实现。不要让所有格式继承一个包含几十个空方法的父类；使用者只应依赖需要的接口。也不要把规则都做成可配置，反而失去审查与验证的确定性。

    练习 类字段都是private 为什么仍可能没有信息隐藏

    如果它把内部可变集合直接返回，或要求调用者知道内部字段组合才能完成业务，外部依旧依赖实现细节。信息隐藏关心变化是否被隔离，private只是其中一种机制。

    16 数据设计 快照 嵌套 引用与并发

    16.1 先分清五种容易混淆的数据 #

    原文版本定义文字和定位基准；个人草稿允许持续修改；个人提交快照是某次确定作答；裁定结果说明选择或重标后形成什么；冻结版与终稿是后续引用的只读依据。它们可能共享部分存储机制，但业务含义不能混在一个不断覆盖的记录中。

    例如甲提交后乙尚未提交，系统不应因为乙继续编辑而改变甲快照。裁定者采用甲的某个答案，也不应把甲原始答案直接改成裁定结果，否则无法知道裁定做过什么。

    16.4 冻结要成为一个一致操作 #

    冻结不是设置frozen=true那么简单。它至少需要：确认操作者职责；确认文书当前状态；确认所需提交与裁定完成；创建确定快照；更新当前有效基准；开放关系轮；记录操作。这些修改应有共同成功或失败的边界。

    如果两个请求同时冻结，系统不应生成互相冲突的两个当前版本。可在事务中锁定工作项后读取状态，或使用revision条件更新并结合唯一约束；具体机制要按数据库实现验证。仅“先查有没有，再插入”仍可能竞争。

    重复请求也要有契约。例如同一冻结修订的重复调用返回已生成版本；不同预期修订号的请求返回冲突。这是幂等和版本检查，不能通过“禁止用户双击”替代。

    16.5 受控回退需要依赖信息 #

    命题从PV-3修订到PV-4后，旧关系仍绑定PV-3，不应偷偷重定向。通过引用与变更映射识别受影响关系，标为待复核；无需变化的关系能否迁移、怎样留下依据，需要确认策略。

    旧终稿继续指向PV-3及原关系结果，新终稿指向PV-4与复核后的关系结果。这样导出历史版本时不会因今天的修改而改变昨天的文件含义。

    16.6 数据库基础要落实到完整性 #

    主键唯一标识记录；外键关联对象并约束引用；唯一约束阻止不应重复的数据；索引帮助查询，但会增加写入和维护成本。事务把一组需要共同成功的修改组织起来。

    一个事务里“先查询再保存”不必然解决并发。两个事务可能都读到旧状态，需要结合锁、带版本条件的更新或数据库唯一约束等机制保证竞争下的正确结果。具体方案在详细设计中确定。

    Controller常负责接收请求和参数映射；Service组织用例与事务；Repository或DAO读写；领域对象表达业务状态与规则。DTO用于边界传输，持久对象对应存储，界面展示对象面向呈现。没有必要在小项目中为每一层都复制相同字段，但要理解边界，避免直接泄露内部对象。

    16.7 一个字符区间的全过程 #

    先固定原文版本TV-1及偏移单位，再记录要素E2覆盖[start,end)。原文规范化、换行替换或插入一个字符，都可能让后续范围变化。不要在展示端悄悄处理后还继续使用旧偏移。

    如果新原文成为TV-2，应明确重新对齐或重标策略。TV-1中的E2不能只改一个text_version_id就假装属于TV-2。显示摘要可以变化，引用基准与原文范围必须有确定对应。

    16.8 乐观并发控制的一次时间线 #

    甲乙都读到工作项revision=7。甲冻结时用“当前仍为7”作为更新条件并成功，revision变为8；乙随后携带7写入时，条件不成立，返回版本冲突。相关快照写入与状态更新仍需同一事务或相应一致性机制，否则可能留下孤立快照。

    悲观锁则先在事务里取得适当锁，再读取、检查和修改。两种方法都需要控制读写范围和失败重试；“用了事务”本身不保证业务检查在竞争下仍成立。

    16.9 迁移与恢复也属于数据设计 #

    新增版本关联字段时，旧数据如何填充、无法确定的数据如何标记、迁移失败怎样恢复，都要事先设计。若数据库已升级，旧程序可能不再兼容；回滚不是简单git checkout。测试中至少验证升级后的关键读写，重要迁移还要演练备份恢复。

    17 Web与构造 把接口契约变成实现

    17.1 前后端分别负责什么 #

    HTML描述页面结构，CSS描述外观与布局，JavaScript处理交互和请求。DOM是浏览器中的文档对象结构，事件让程序响应点击和输入。组件化前端进一步把界面拆成可组合单元；先理解状态与数据流，再学习具体框架。

    后端接收请求、验证身份与业务条件、组织计算和读写数据，再返回响应。数据库负责持久保存和约束。前端显示“已保存”只有在真实请求与保存结果对应时才有依据。

    17.2 一次创建关系请求的全过程 #

    用户选好来源、目标与类型后，前端组装数据并发送HTTP请求；服务端检查登录和文书分配，读取当前状态与基准版本，校验结构，在事务内保存；然后返回关系ID、修订号与展示状态；前端依据响应更新列表。

    HTTP方法表达操作语义：GET用于读取，POST常用于创建或发起操作，PUT常用于对目标资源整体替换，PATCH用于部分更新，DELETE用于删除。具体接口还要有统一契约；不能因为使用POST，就假设重复请求一定只执行一次。

    JSON是结构化的数据表示，字段必须有约定。服务端不能只信任前端传来的userId或“我是裁定者”；应根据认证上下文和当前分配判定权限。

    17.3 状态码与业务结果 #

    常见示例：200表示请求成功，201常用于创建成功，400表示请求本身有问题，401用于未通过身份认证，403用于无权操作，404用于资源未找到，409可用于状态或版本冲突，500表示服务端错误。项目应约定具体使用方式，不同错误还需要稳定的业务错误码与可理解说明。

    “已登录”“是关系标注员”“被分配到该文书”“当前阶段可写”“版本有效”是不同检查。前端门禁改善体验，后端检查保障执行，数据约束与事务保障一致性。

    17.4 构造包括编码之外的工作 #

    软件构造涉及详细实现、调试、单元测试、构建与集成等活动。代码应清晰表达意图：名字说明对象和动作；函数保持职责集中；错误处理与业务结果明确；不要用大量隐藏副作用和魔法数字制造理解成本。

    防御式编程检查外部和不可信输入，对非法状态给出明确处理；契约式设计明确调用者与被调用者的责任。不能用“捕获全部异常然后返回成功”掩盖错误，也不能只弹出“失败”而不保留可恢复输入和定位信息。

    当条件分支围绕固定规则反复出现时，可考虑表驱动：把“状态—操作—允许职责”集中成可审查的数据或规则映射。它能减少散落的条件，但仍要说明优先级和不支持组合，不能把复杂业务盲目塞进一张巨大表。

    17.5 按一条完整业务链做增量 #

    先完成一条小而完整的链路，例如“登录后领取文书 → 保存类型草稿 → 刷新后恢复”，再扩展多人提交、裁定和冻结。这样能尽早验证接口、数据与部署连接。

    只把所有页面画完，再把所有后端写完，最后联调，会把接口不一致和流程误解集中到项目末期。每个增量都应有明确的完成条件，并实际集成运行。

    重构是在保持外部可观察行为的前提下改善内部结构。改名、提取职责、消除重复都可以是重构；新增回退功能改变行为，属于功能变更，不能仅称为重构。结对编程强调两人共同观察和思考，不是把工作简单分成一个人写、另一个人完全不看。

    17.6 先把接口契约说清楚 #

    以下路径是教学命名，不表示现有项目已经使用它们。

    接口示例输入和结果要点关键失败情况
    POST /tasks创建草稿，返回任务ID无创建职责、参数无效
    POST /tasks/{id}/publish携带期望配置修订，发布工作项指南未确认、原文或分配缺失
    PUT /versions/{id}/draft保存本人可写草稿，带预期修订非本人、已提交、修订冲突
    POST /versions/{id}/submit提交某一确定个人版本必填未完成、基准失效
    POST /work-items/{id}/freeze带预期工作项修订，返回冻结ID提交不齐、裁定未完、版本冲突
    POST /relation-versions/{id}/relations类型、操作数、命题基准，返回关系ID与修订越权、阶段不对、引用不合法
    POST /work-items/{id}/finalize确认完整关系结果，返回终稿ID遗漏未处理、基准不一致
    POST /final-snapshots/{id}/exports格式，返回文件结果或导出任务无权、终稿无效、生成失败
    POST /exercises/{id}/attempts创建学生个人尝试未开放、不可见、已截止

    接口契约还应定义认证方式、字段类型、错误码、重复请求、事务结果、分页或大小限制，以及异步任务状态。表里的“版本冲突”可以用409等约定响应，但最终采用什么状态码与错误结构要全项目统一。

    17.7 先完成最小的真实贯通 #

    第一步，使用测试材料建立文书和指南版本，前端能读取。第二步，一个账号保存草稿，刷新后仍存在。第三步，第二个账号拥有独立草稿且看不到第一人的未开放答案。第四步，提交后能查到固定快照，状态推进依据真实所需分配计算。

    有了这条链，再做裁定、冻结与关系写入。否则后面看到的“人数”“差异”“定稿”可能一直只是前端变量，直到联调才发现数据模型不支持业务。

    17.8 冻结服务的教学伪代码 #

    freeze(workItemId, expectedRevision, actor):
  begin transaction
  item = loadWorkItemWithConcurrencyControl(workItemId)
  require actor has proposition adjudication duty for item
  if same adjudicated revision already frozen:
      return its snapshot under the agreed retry policy
  require item.revision == expectedRevision
  require item.state == PROPOSITION_ADJUDICATION
  require all required independent submissions exist
  require unified cut is confirmed
  require adjudication and completeness checks passed
  snapshot = createImmutablePropositionSnapshot(item)
  item.openRelationRound(snapshot.id)
  save item and audit record
  commit
  return snapshot.id and item.revision

    这是说明执行顺序的伪代码，不是可直接运行的Java。真正实现要用一致的锁或版本机制、异常与事务处理，重复冻结的识别范围还需契约。失败时回滚，不允许快照创建失败却已开放关系轮。

    17.9 关系写入的教学伪代码 #

    createRelation(personalVersionId, request, actor):
  begin transaction
  load writable version and current work item consistently
  require version belongs to actor and the current work item
  require actor is assigned to the relation round
  require work item allows relation editing
  require request.baseId matches the valid frozen base
  validate type, members, typed references and nesting
  save relation and advance structure revision
  commit
  request rendering for this exact structure revision
  return relationId, revision and renderingStatus

    这里的“一致读取”很关键：若校验后另一个事务就回退了命题，保存仍应能够检测冲突。事务边界、锁或条件写要与流程更新互相协调。渲染可以在提交后执行或排队，失败不应让客户端误以为关系从未保存。

    17.10 错误需要让人知道下一步 #

    “BASE_VERSION_EXPIRED”可提示“命题基准已更新，输入已保留，请复核后关联新版本”；“PENDING_SUBMISSIONS”列出仍缺哪些提交；“REFERENCED_RELATION”列出哪些外层关系依赖当前对象。

    不要把全部业务失败变成500，也不要把所有失败都返回200并靠一段文字判断。网络断开后结果未知时，应提供查询或幂等重试机制；不能仅再次创建来试运气。

    18 测试 从规则到有区分力的证据

    18.1 从需求开始设计预期 #

    测试通过执行并比较预期与实际，发现缺陷和提供质量信息。它通常不能证明一个复杂系统不存在任何缺陷。测试用例需要前置条件、输入或动作、预期结果和可重复的检查方式。

    同一个需求可以在不同层次验证：单元测试检查局部规则；集成测试检查模块、接口与真实存储协作；系统测试检查完整系统；验收测试检查是否满足用户约定。黑盒与白盒是设计测试的视角，与这些测试层次不是一一对应关系。

    18.2 黑盒方法怎样选 #

    等价类把预期行为相似的输入归组，再选择代表。关系成员至少两个时，可分为0个、1个、合法多个、重复成员、引用不存在等类别。边界值关注条件两侧，例如最小成员数2附近的1、2、3；不能把所有异常都叫边界值。

    决策表适合多个条件共同决定结果：有权限吗、阶段正确吗、基准有效吗。状态转换测试检查哪些状态允许哪些操作，既测合法转换，也测非法转换。场景测试按用户目标走完整链路；探索性测试在学习系统时动态设计操作，适合发现规格遗漏和交互问题。

    18.3 白盒覆盖不是质量结论 #

    语句覆盖检查可执行语句是否执行，分支覆盖检查各判断结果是否经历，路径覆盖关注执行路径。循环会造成大量甚至无限路径，完整路径覆盖通常不可行。

    例如条件“hasPermission && isRelationRound”在某语言里是一段复合判定。让整体判断分别为真和假，可以达到判定分支覆盖，但不代表每个子条件及短路组合都充分测试。覆盖报告要说明统计口径。

    100%语句覆盖仍可能缺少断言、遗漏业务规则或没有并发场景。测试的价值在于错误实现能否被区分。例如“返回非空”抓不到版本错误，“新关系基准ID等于指定冻结版本ID”才更有判断力。

    18.4 桩 驱动与Mock #

    桩（Stub）替代被测对象依赖的下层，返回预设结果；驱动（Driver）替代调用被测对象的上层，主动发起调用；Mock还常用于验证预期的交互，例如是否调用保存以及调用参数。

    测试冻结协调逻辑时，可以用仓储替身快速检查非法状态不会保存。但要证明事务、唯一约束和并发竞争有效，还需要使用实际数据库行为的集成测试。不能把所有依赖都Mock掉后宣称整个系统已经可靠。

    18.5 缺陷 回归和测试驱动 #

    发现缺陷后记录环境、步骤、输入、预期、实际、证据和影响。修复时先构造能暴露该缺陷的复现，再修改，运行相关回归；必要时扩大到受影响链路。回归测试检查修改是否破坏原有行为。

    测试驱动开发通常采用“先写失败测试 → 最小实现使其通过 → 重构”的循环。它有助于接口与可测性设计，但不能替代需求确认和系统测试。

    测试报告要区分通过、失败、未执行、阻塞。计划测试多少项与实际跑过多少项不是一回事；覆盖率也需要真实工具报告及口径，不能填一个理想数字。

    本章自测：测试“未冻结不能新增关系”时，除了检查返回错误，还要检查什么？

    展开答案

    检查没有新增关系、没有错误推进状态、既有草稿未被破坏，且返回原因与当前条件一致。还应考虑请求来自绕过前端的接口调用，以及页面读到旧状态的情况。

    18.6 先准备可复现的测试场景 #

    准备一份短文书、一个明确指南版本、两名命题标注员、一名命题裁定者、两名关系标注员和一名关系裁定者；角色能否兼任按测试用例设定。再准备教师、学生、标准和练习。使用可重复初始化的测试数据，避免每个测试依赖上一轮手工操作。

    测试数据与业务预期应人工核对。不能让同一个错误规则既生成实现，又生成“正确答案”，否则测试可能全部通过但业务仍错。

    18.8 把测试分配到合适层次 #

    单元层重点测试关系成员数、方向、版本匹配和状态规则，使用依赖替身提升定位速度。服务集成层使用真实存储验证事务、唯一约束、并发冻结、跨账号与跨版本拒绝。系统层从不同账号完成整条流程，检查显示、恢复与文件。

    测试两个账号隔离，不只是换一个前端名字。应在两个独立会话里发出真实请求，检查服务端返回与存储归属；接口查询也不能泄露隐藏作答。

    18.9 一条测试应该怎样写得有判断力 #

    以T07为例：初始化状态为命题待裁定、无冻结基准；用已分配关系标注员身份直接请求创建关系；断言返回约定错误；查询关系数量不变；检查状态未推进；已有草稿仍可读取。

    只断言“页面出现提示”无法证明后端没写。只断言HTTP失败也可能是别的错误，例如数据格式先错了，根本没测到冻结门禁。测试输入应满足其他条件，专门触发要验证的规则。

    18.10 文件与图示要单独验收 #

    JSON检查能解析、版本齐全、ID唯一、引用存在、嵌套不丢失；表格导出检查命题和关系怎样分表，普通邻接矩阵不足以完整表达嵌套；SVG或图片检查中文、方向、实心空心、加号、斜线和多结构布局。

    还应比较文件与同一终稿快照，防止命题读新版、关系读旧版。若要求无损往返，再导入后应比较结构语义，不能仅比较原JSON字符串是否字节完全相等。

    18.11 缺陷报告和结果怎么记录 #

    缺陷包含环境、版本、复现步骤、预期与实际、证据和影响。修复后补能暴露问题的回归用例。测试报告分别列已通过、失败、未执行、阻塞，附实际命令或操作与记录。

    不要把上面24条复制进报告后全部填“通过”，也不要编造覆盖率。本讲义提供的是测试设计起点，你要用真实执行把它变成证据。

    18.12 用决策表设计冻结测试 #

    先按确定优先级检查权限、状态、版本，再检查提交与裁定。下面的“任意”表示该行结果不依赖此条件，不表示生产代码可以跳过其他必要安全检查。错误优先级是教学约定，需要项目统一。

    权限有效阶段正确修订有效提交与裁定完成结果
    否任意任意任意拒绝且不改变数据
    是否任意任意状态不允许
    是是否任意版本冲突
    是是是否缺失条件
    是是是是生成快照并推进

    对每个拒绝行，构造其他条件尽量正确的输入，避免请求因为无关字段错误提前失败。再增加重复和并发请求，以及事务中写入失败等场景。

    18.13 区分断言业务和重复实现 #

    不好的测试把生产代码的同一段if复制到测试，再比较两边计算结果；两边可能一起错。更好的测试从需求给出独立预期：未冻结返回约定错误、关系数量不变、工作项不推进、原草稿仍在。

    18.14 一份缺陷记录的示范 #

    教学缺陷BUG-01：在命题待裁定状态直接调用关系接口，接口返回成功并新增记录。期望是拒绝且数据不变。初步根因是仅前端隐藏按钮，服务端只校验角色。修复方案是增加工作项状态与基准校验，补接口回归，并检查其他写入口。实际项目必须以真实复现和日志为准，不能把这个示范填成已经发现的缺陷。

    18.15 覆盖率为什么必须配合业务检查 #

    一个方法每行都执行过，也可能没有测试另一文书的引用，或没有断言实际保存的base_id。覆盖率回答哪里被运行，需求追踪回答什么约定被验证，变异或错误注入帮助检查测试能否抓错。它们提供不同证据，不能互相代替。

    19 变更与AI协作 追踪 判断与纠偏

    19.1 给AI一个能验收的任务 #

    一份任务说明应包含背景与目标、相关来源、允许修改的范围、输入输出、关键约束、验收方式和禁止自行猜测的事项。将大任务分成可独立审查的步骤，并提供实际项目上下文。

    例如：“实现冻结前拒绝新增关系。工作项状态由服务端读取；不得新增绕过接口；使用已有错误格式；补充非法状态、合法状态和版本过期三个测试；说明修改的文件与结果。”这比“帮我把系统完善一下”更容易检查。

    采用“明确任务 → 生成或实施 → 人工审查 → 运行验证并纠正”的闭环。AI生成的需求不能充当真实访谈，生成的代码不能自行证明正确，生成的测试也可能与错误实现采用同一个假设。人要保留独立的业务预期。

    19.2 过程记录要体现判断 #

    日志不仅记录用了什么工具，还应记录提供了什么上下文、发现什么错误、怎样判断和修改，以及运行证据。不要为了完整而编造访谈、测试、会议或人工审查；尚未执行的步骤应保持待完成状态。

    19.3 用AI时怎样保持自己能解释 #

    一次只委派一条可验证规则，把用例、版本约束、错误格式与允许改动范围提供进去。审查它是否绕开了业务层、只检查前端、覆盖旧版本、把多态引用压成两个P编号，或给出只会证明自身实现的测试。

    记录真实发现和修改。例如“生成代码只检查frozen字段，漏了工作项分配；补充未分配用户直接调用接口的测试并修正服务端”。这类记录能展示工程判断，不能由本讲义替你编造成已经发生的过程。

    19.4 以四阶段改为六阶段为例 #

    首先记录变更：正式标注拆成命题与关系两轮，中间增加命题裁定冻结，后面保留关系裁定定稿。说明来源与确认状态，而不是把历史文档删掉让人看不到变化。

    然后检查角色与用例：标注与裁定职责需分轮，关系用例加冻结前置；检查领域模型：增加个人轮次版本、冻结基准；检查动态模型：更新状态与顺序；检查设计与实现：调整服务、表、权限和接口；检查测试与文档：增加非法状态、旧基准及回退场景。

    19.6 AI过程材料怎样写得可信 #

    可以围绕一个真实错误讲清：给了什么材料；AI生成了什么；通过哪个业务依据发现错；改了哪些地方；用什么验证。比如“把M当无方向连接”或“将学生练习并入正式库”，都需要展示实际过程，而不是照抄本讲义例子。

    日志不要求把每次聊天都重新叙述成作文，但应能定位关键任务、输入、输出、审查和修正。课程若有指定契约与提交标记，应按该任务要求落实。

    19.7 修订后再做一次横向检查 #

    同一个词是否同义：要素、命题、标注版本、冻结版、终稿是否区分；同一条规则是否统一：指南、SRS、原型和代码中的SM-C、切割、M方向、J约束与回退策略是否一致；同一数据是否同源：界面、接口和导出是否引用同一版本。

    19.8 需求变更的一次完整传播 #

    假设批准增加“冻结后可受控修订”。先记录旧约定和新目标；分析权限、状态、版本、关系依赖、导出与教学是否受影响；更新用例中的回退流与状态转换；设计新修订和复核标记；实现接口与存储；运行旧版可查、越权拒绝、影响关系复核和历史导出的测试；更新手册与基线。

    如果只改页面提示为“已生成新版本”，而没有新的ID、不可变历史和引用变化，这条变更没有真正完成。追踪矩阵让这种断链变得可见。

    19.9 与AI协作时保留独立判断 #

    让AI先列出不确定点和来源，再限定已确认规则；让它实现一条明确契约，再人工审查差异；测试预期先来自业务与样本，不从实现倒推。发现问题时区分需求不清、上下文不足、模型推断错误和实现缺陷，后续改进才有针对性。

    如果测试失败，不应让AI通过删断言或把预期改成当前结果来“修复”。先确认预期是否正确，再判断应该改测试、代码还是需求。每次修改都留下理由与实际验证。

    20 交付与维护 让别人能用 以后能改

    20.1 安装和部署都需要可复现 #

    安装通常把程序放入目标环境；部署还包含配置应用、数据库、网络、权限、数据迁移与运行检查。目标环境不同于开发环境时，路径、时区、字符集、依赖和权限都可能导致问题。

    可交付材料需要说明环境要求、配置示例、数据库初始化与升级、启动和健康检查、初始账号、安全配置、备份与恢复、故障排查。不要把本机密码或真实密钥写进仓库；示例配置与真实环境配置应有明确边界。

    发布后用冒烟测试检查核心功能。回滚不仅是换回旧代码，还要考虑新数据库结构与旧代码是否兼容。数据已经被新版本修改时，恢复策略必须在发布前设计并验证。

    20.2 文档有不同读者 #

    用户文档教使用者怎样完成任务，重点是角色、入口、步骤、反馈和常见错误。系统文档帮助开发与维护人员理解结构、接口、数据、部署和决策。把一份API列表交给法学教师，通常不能算完成使用培训。

    验收演示可以选一份样本，完整走过创建、标注、裁定、冻结、关系、定稿和文件检查。然后让另一位同学按说明从干净环境启动。这比只展示自己的桌面和成功截图更能证明交付能力。

    20.3 维护的四种常见类型 #

    类型主要动机案例
    修正性修复已存在缺陷修复导出关系引用丢失
    适应性适应环境变化适配数据库或运行环境升级
    完善性满足新增或改进的用户需要新增按案例类型筛选
    预防性降低未来故障与修改困难拆分过大的模块并补回归测试

    维护同样需要需求分析、影响分析、设计、实现、验证与发布。逆向工程从已有系统提取理解或更高层表示；再工程在理解基础上改造系统。技术债表示为了当前交付而承担的后续额外成本，需要记录原因、后果、偿还条件和优先级，而非把所有欠完善之处笼统称为债务。

    一次故障的根因分析应解释触发条件、为什么现有设计或验证没阻止、怎样修复与预防。只写“成员粗心，今后注意”不能改变系统性问题。

    20.4 交付清单怎样组织 #

    需求材料解释为什么做以及边界；分析模型解释业务对象和行为；设计材料解释架构、职责、接口和数据；源码与构建支持复现；测试材料证明实际验证；运行文档支持部署、使用和维护；过程记录证明决策和贡献。

    交付的核心是相互一致。顺序图写两个独立账号，演示却只在一个共享数组里换名字，就不符合模型；报告写版本可追溯，数据库却覆盖旧记录，也不符合需求。

    20.5 一条可复现的演示脚本 #

    先展示材料与指南版本，创建并发布一份测试文书；两个账号完成切割与命题提交；裁定者确认统一结果并冻结；关系标注员建立包含嵌套的结构；关系裁定者检查完整性并定稿；导出并打开实际文件，核对版本。

    再展示一个失败例子：未冻结调用关系接口被拒绝，或携带过期基准提交被拒绝。然后展示教学练习，说明学生作答不改变正式数据，反馈绑定哪份标准。如果受控回退已纳入范围并实现，再演示旧版保留与关系复核。

    不要在演示前手工把数据库改成目标结果却不说明初始化方式。可以预置测试账号和材料，但核心业务行为要能真实发生。

    20.6 让另一位同学从环境说明启动 #

    运行说明应包括依赖、配置、数据库迁移、启动顺序、地址、初始账号、文件存储、常见错误和停止方式。发布时记录代码版本、配置与数据版本；准备备份、恢复和回滚，尤其说明数据库变化是否允许直接回到旧程序。

    用户手册按任务教：创建者怎样发布，标注员怎样提交，裁定者怎样确认，教师怎样发练习。开发手册按结构教：模块、接口、表、约束、关键决策和故障排查。两种读者不应被同一堆内部类名淹没。

    20.7 答辩时可以怎样解释自己的设计 #

    问“为什么分两轮”，回答共同命题基准与可比性；问“为什么保存稳定ID”，回答重编号不能改变身份；问“为什么需要新版本回退”，回答旧结果可复现与关系依赖；问“前端不是已经禁用了吗”，回答后端才是执行权限与状态约束的地方。

    每个回答最好接一个可观察证据：一条接口、一个版本记录、一个失败用例或一个实际文件。不会的部分如实区分已实现、已设计、待确认，工程判断比用术语掩盖空白更有价值。

    20.8 用一条来源链演示可信交付 #

    打开一份终稿导出，指出它的finalSnapshotId；由此找到冻结命题版本与关系结果；再找到对应原文、指南与裁定记录；最后说明哪些测试验证了这条链。这样答辩者看到的是可核对的对象，而不是“我们做了版本管理”的口头陈述。

    20.9 软件交付后的第一项新增需求 #

    假设教师需要增加一种练习反馈。先确定它改变的是标准、尝试还是展示；查看已有历史是否需要重新计算；决定新旧反馈的版本范围；更新接口与测试后再发布。维护阶段仍然沿着需求、设计、实现、验证的循环工作。

    20.10 发布前最小核对清单 #

    指定代码与配置版本；数据库迁移已验证；关键流程冒烟通过；账号和权限正确；文件目录可读写；日志能定位问题；备份恢复有依据；用户知道怎样使用与报告故障。根据真实系统调整，不能把“清单已勾选”当成实际执行证据。

    21 过程模型 按风险和反馈组织增量

    21.1 活动与过程模型不是一回事 #

    需求、设计、实现、测试是活动。过程模型决定这些活动以什么顺序、怎样反复、何时交付。选了迭代开发也要做需求和设计；选了顺序流程也应尽早考虑测试和风险。

    模型组织特点适用考虑与局限
    边做边改直接实现，遇到问题再补小实验启动快；缺少结构和受控过程，规模扩大容易失控
    瀑布阶段顺序推进，形成评审产物需求相对稳定时便于管理；晚发现问题时返工成本高
    增量分批增加可用功能较早交付价值；需要接口与整体结构支持逐步扩展
    迭代对已有认识和方案反复改进适合逐步学习；需要控制每轮目标和变更
    演化根据反馈持续形成产品与需求适合不确定需求；容易积累结构问题，需持续重构
    原型通过样例探索需要或技术能降低不确定性；要明确原型是否抛弃或继续演化
    螺旋围绕目标、风险分析、开发验证和下一轮计划反复风险驱动；需要较强的风险识别与管理能力

    增量与迭代经常结合：本轮新增关系标注是增量，同时改进上轮命题工作台是迭代。敏捷强调反馈、协作、应对变化与可用软件，不代表不写文档、不做设计或没有计划。

    21.2 怎样用于这门课 #

    学习顺序可以从需求一路到交付，实施则采用几个可运行增量：单人基本标注；多人独立提交与裁定；冻结和关系；教学与导出；质量与交付完善。具体范围依据已确认任务要求调整。

    每轮都包括小范围需求确认、设计、实现、测试和回顾。质量、配置与追踪始终贯穿，不要把“P6质量保障”误读为前面五个阶段可以先不管质量。

    21.3 把过程模型用在同一份作业上 #

    首轮做可持久化的单人标注，是一个增量；次轮增加独立提交、裁定与冻结，是另一个增量；重新设计不清楚的保存反馈，是迭代。每轮都有小规模需求、设计、实现与测试，而不是把需求只留在第一轮。

    若嵌套图示是高风险点，可以先做实验原型验证可行性，再决定正式实现。这个风险试验可能不直接交付新用户功能，却能减少后续返工。过程选择应服务于不确定性和交付目标。

    22 综合复习 用同一案例串起全部产物

    22.1 用同一条规则检查自己是否真的理解 #

    请不看答案，解释“命题裁定并冻结后才能标关系”的完整链路：用户为什么需要它；需求怎样写；用例在哪里体现；领域模型需要哪些版本；系统顺序图有什么事件；详细顺序图谁校验；数据库怎样约束；接口如何返回冲突；测试怎样证明；旧版本怎样保留。

    如果某一步只能说术语，却讲不清本案例怎么做，就返回对应章节。会默写“高内聚低耦合”还不够，要能指出具体哪两项职责应该分开，以及这样分开后哪种变化更容易处理。

    22.2 常用术语速查 #

    术语简单解释
    SRS软件需求规格说明书，约定系统需要做什么
    SSD系统顺序图，以黑箱表达外部事件
    DFD数据流图，表达数据经过哪些处理
    ERD实体关系图，表达数据概念与联系
    UML用于表达结构和行为的一组建模语言符号
    API对外提供操作和数据交换的接口
    ADR架构决策记录，保存方案的理由和后果
    DTO跨边界传输的数据对象
    CI持续集成中的自动构建和检查
    回归测试修改后检查原有行为有没有被破坏
    基线经评审并受控的后续工作依据
    幂等相同操作重复执行，在约定范围内不产生额外业务效果

    最后一题：别人问你“为什么先学需求，再学设计”时，可以这样回答：需求先约定目标和约束，设计再选择实现这些约定的结构；两者通过原型、模型和验证不断相互校正。目标不清时，写得再快也可能做成另一个系统。

    22.3 学完后应能回答的十个问题 #

    1. 开发流程和标注业务流程有什么区别？
    2. 为什么先统一切割，再比较标签？
    3. 为什么关系标注必须绑定冻结命题版本？
    4. 系统顺序图和详细顺序图各画什么？
    5. 学生练习为什么不进入正式终稿？
    6. 显示P3和稳定ID有什么区别？
    7. 为什么两列命题ID不能表达所有嵌套关系？
    8. 回退为什么不能只把阶段变量改小？
    9. 哪些测试能证明前端门禁之外的后端规则？
    10. 如何从一份导出文件找到它使用的指南、原文、命题和关系版本？
    展开参考回答

    1 开发流程是工程师怎样做系统，业务流程是用户怎样使用系统。2 边界不同会让标签和关系无法直接比较。3 所有人需要共享同一批可重现对象。4 前者画外部事件与黑箱，后者画内部职责协作。5 教学有标准与反馈，正式模式是在形成新结果。6 显示序号可变，身份引用稳定。7 关系可有多个成员，也可引用其他关系。8 必须保留旧快照、权限和依赖复核。9 直接接口、数据不变、并发与跨版本等测试。10 导出带版本元数据，终稿关联到具体快照与来源记录。

    22.4 一次综合练习 #

    给定变化：“关系轮开始后发现统一命题集有边界错误，需要纠正，但历史导出必须可复现。”请依次写出需求、参与者、用例异常流、状态转换、概念与关联、接口、事务、关系影响和测试。

    参考推导

    需求明确受控修订与历史可读；参与者区分申请者和命题裁定职责；异常流保留当前作答并发起申请；状态模型新增受控修订路径；数据形成新原文或命题版本并保留旧引用；接口带预期版本和理由；事务保证新基准生效与状态一致；关系按依赖标待复核；测试覆盖越权、并发、旧导出不变、新终稿绑定与影响提示。具体申请批准规则仍需需求方确认。

    22.5 判断自己是否已经学会 #

    你能够用一个短样本解释所有图，能够指出同一规则在不同产物中的位置，能够设计会让错误实现失败的测试，并能说清已确认、示例和待决定的边界，就已经建立了软件工程的基本工作方式。下一步是亲自完成一个小增量，再带着真实问题回到讲义查阅。
